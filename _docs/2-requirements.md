## 1) 목적

통화 중 발생하는 고객 질의에 대해 **1초 이내에 근거 문서를 상담원 화면에 제시**하는 시스템을 구축한다.
단순히 동작하는 데모가 아니라, **품질을 수치로 측정하고 회귀를 자동으로 막는 체계**까지를 개발 범위에 포함한다.

## 2) 개발 범위

### 포함

| 구분 | 내용 |
|---|---|
| 음성 | 스트리밍 STT 연동, 화자 분리, 발화 구간 검출 |
| 검색 | 문서 수집·청킹·색인, 형태소·벡터 하이브리드 검색, 리랭킹 |
| 실시간 | 검색 트리거 판정, WebSocket 양방향 전달, 레이턴시 최적화·캐싱 |
| 생성 | 근거 기반 요약 카드, 출처 표시, 근거 부족 시 거절 |
| 분류 | 컴플라이언스 위반 표현 분류기 파인튜닝 |
| 후처리 | 상담 요약, 문의 유형 분류, 지식베이스 공백 리포트 |
| 평가 | 골든셋 구축, 자동 채점 하네스, 오류 주입 실험, CI 연동 |

### 제외

| 제외 항목 | 사유 |
|---|---|
| OpenCV 기반 영상 처리 | 본 주제에 활용처가 없다. 억지로 끼워넣지 않는다 |
| 자체 통화 녹음 수집 | 개인정보 문제. 공개된 저작권 해결 데이터만 사용 |
| 약관 원문의 공개 게시 | 저작권. 화면·문서에는 요약·해석 + 출처만 |
| 실제 콜센터 회선(PBX/CTI) 연동 | 8주 범위 밖. 브라우저 오디오 입력과 녹음 파일 재생으로 대체 |
| 상용 수준의 다중 통화 동시 처리 | 성능 목표는 단일 통화 기준으로 측정 |

## 3) 음성 데이터 수집 및 연계

| 요구 | 내용 |
|---|---|
| A-1 | Google STT 스트리밍 인식, 부분 결과(`is_final: false`) 포함 수신 |
| A-2 | 화자 분리 — 고객 / 상담원 구분 |
| A-3 | 브라우저 ↔ 게이트웨이 오디오 청크 및 자막 전달 (WebSocket) |
| A-4 | 발화 구간 검출 — 침묵 판정 (직접 구현) |

**평가용 음성**은 AI Hub 공개 데이터를 1순위로 사용한다. 승인에 시간이 걸리므로 **1주차 즉시 신청**한다. 승인 지연 시 2순위로 TTS 합성을 병행 준비한다. 상세는 [골든셋 설계]({{ '/docs/golden-set/' | relative_url }}).

반복 실험은 **녹음 파일 배치 모드**로 수행하고, 스트리밍 API 는 실시간 데모에만 사용한다 (비용 통제).

## 4) 실시간 문서 추천 처리 — RAG 핵심

| 요구 | 내용 |
|---|---|
| B-1 | **검색 트리거 판정** — 언제 검색할지 결정 |
| B-2 | **하이브리드 검색** — nori 형태소(BM25) + dense_vector, RRF 병합 |
| B-3 | 리랭킹 — 상위 후보 재정렬 |
| B-4 | 근거 기반 요약 카드 생성 |
| B-5 | 출처 표시 — 문서명 + 조항 + 유사도 |
| B-6 | 근거 부족 시 **"관련 문서 없음"** 반환 (지어내지 않음) |

### 난제 ① 트리거 판정 — 언제 검색할 것인가

일반 RAG 는 완성된 질문을 받지만 스트리밍은 그렇지 않다.

```
0.4초  "아"
0.9초  "아 저번에"
1.6초  "아 저번에 가입할"
2.4초  "아 저번에 가입할 때 6개월"
3.1초  "아 저번에 가입할 때 6개월 할인 된다고 했는데"
```

매 조각마다 검색하면 서버 과부하·카드 깜빡임·비용 폭증, 너무 늦으면 대화가 이미 넘어간다.

| 전략 | 방법 | 예상 문제 |
|---|---|---|
| 침묵 기반 | N초 무음 시 검색 | 말이 느린 고객에서 지연 |
| 종결어미 기반 | "~요", "~까요", "~는데" 패턴 | 중간에 끊어 말하면 오발동 |
| 길이 기반 | 토큰 N개 누적 시 | 의미와 무관하게 발동 |
| 분류기 기반 | 질문 완결 여부 판정 모델 | 학습 데이터 필요 |
| 하이브리드 | 위 조합 + 디바운싱 | 튜닝 복잡 |

3주차에 침묵 기반 v1 을 먼저 만들고, 트리거 정확도·발동 지연·불필요 발동률을 측정하며 개선한다.

### 난제 ② STT 오류 내성 — 본 사업의 대표 실험

| 실제 발화 | STT 결과 | 문제 |
|---|---|---|
| 해지 | 해제 | 완전히 다른 조항이 검색됨 |
| 요금제 | 요금 제 | 띄어쓰기로 형태소 분해 실패 |
| 위약금 | 위약 금 | 동일 |
| 자동이체 | 자동 이체 | 동일 |

Elasticsearch 를 쓰는 근거가 여기서 나온다. 한 엔진 안에서 네 가지를 동시에 처리할 수 있다.

```
1. nori 형태소 분석기 → 띄어쓰기 오류 흡수
2. 자모 분해 필터      → 유사 발음 오인식 대응
3. dense_vector 필드   → 의미 기반 검색
4. RRF 병합            → 위 결과 통합
```

**대표 실험**: 오류율 0~20% 를 인위 주입하며 BM25 / 벡터 / 하이브리드의 Recall@5 를 비교한다. 측정 현황은 [진행 상황]({{ '/progress/' | relative_url }}).

### 난제 ③ 레이턴시 예산

트리거 발동 → 카드 표시까지 **1초 이내**.

| 단계 | 목표 | 최적화 수단 |
|---|---|---|
| 트리거 판정 | 10ms | 규칙 우선, 모델은 캐싱 |
| 검색 | 150ms | 인덱스 워밍업, 필드 최소화 |
| 리랭킹 | 200ms | 상위 20개만, 배치 추론 |
| 생성 | 500ms | 스트리밍 출력, 프롬프트 캐싱 |
| 전송 | 50ms | WebSocket 유지 연결 |

추가로 자주 나오는 질문의 검색 결과를 캐싱하고, 통화 시작 시 고객 정보 기반 사전 인덱싱을 검토한다.

## 5) 상담원 지원 화면 기능

| 요구 | 내용 |
|---|---|
| 자막 | 화자별 실시간 자막. 부분 결과는 갱신, 최종 결과는 확정 표시 |
| 추천 카드 | 출처 없는 카드는 표시하지 않는다. 카드가 없으면 "관련 문서 없음" |
| 경고 | 컴플라이언스 감지 시 발생 시각과 권장 대체 표현 함께 표시 |
| 연결 | WebSocket 유지 연결. 끊김 시 재연결 및 세션 복구 |

메시지 규격은 [인터페이스 계약]({{ '/docs/interface-contract/' | relative_url }})이 정본이며, 1주차 안에 확정한다.

## 6) 시스템 아키텍처

전체 구성도와 도구별 역할은 [시스템 아키텍처]({{ '/docs/architecture/' | relative_url }}) 참조.

요약: React 대시보드 ↔ WebSocket ↔ Node.js 게이트웨이 → (Google STT) → FastAPI 코어(트리거·검색·생성·컴플라이언스) → Elasticsearch / LLM / 분류기, 메타데이터는 MySQL.

## 7) 보안 및 개인정보 보호

| 항목 | 요구 사항 |
|---|---|
| 민감정보 마스킹 | 통화에 섞이는 카드번호·주민번호·계좌번호는 저장·표시 전에 마스킹한다 |
| 데이터 출처 | 자체 녹음을 수집하지 않는다. AI Hub 등 저작권·개인정보가 해결된 공개 데이터만 사용 |
| 저작권 | 약관 원문은 검색 인덱스 내부 저장까지만. 화면·공개 문서·발표 자료에는 요약·해석 + 출처 표시 |
| 자격증명 | API 키는 `.env` 로 관리하며 저장소에 커밋하지 않는다 |
| 답변 범위 제한 | LLM 은 인덱싱된 문서 범위 밖의 정책·보상을 말하지 않는다. 근거 부족 시 "관련 문서 없음" |
| 공개 경계 | 본 저장소는 GitHub Pages 로 공개 게시된다. 커밋이 곧 발행이다 |
