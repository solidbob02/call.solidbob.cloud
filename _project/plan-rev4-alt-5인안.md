## 1. 주제 선택 근거

### 1.1 투입자원 목록이 이미 답을 가리킨다

과정에서 제시된 투입자원 중 **Google Speech-to-Text API**와 **WebSocket**은 리뷰 감정 분석 주제에서는 쓸 데가 없다. 이 두 도구가 목록에 있다는 것은 콜센터 주제를 염두에 둔 구성으로 보인다.

| 도구 | 콜센터 주제 | 리뷰 감정 분석 |
|---|---|---|
| Google STT | 필수 | 불필요 |
| WebSocket | 필수 | 불필요 |
| Elasticsearch | 핵심 | 선택 |
| HuggingFace | 활용 | 활용 |

### 1.2 "통화 후" 대신 "통화 중"

흔한 콜센터 프로젝트는 통화 녹음 파일을 사후 처리한다(전사 → 요약 → 티켓 생성). 이는 사실상 **배치 파일 변환 파이프라인**이며 WebSocket이 필요 없다.

본 프로젝트는 **통화가 진행되는 중에 개입**한다. 이 차이가 기술 난이도와 프로젝트 가치를 결정한다.

| | 사후 처리형 | 실시간 개입형 (본 프로젝트) |
|---|---|---|
| 입력 | 완성된 녹음 파일 | 0.3초 단위 스트리밍 조각 |
| 질의 | 완결된 문장 | 미완성 발화 |
| 레이턴시 요구 | 없음 | 1초 이내 |
| RAG 난이도 | 낮음 (일반 RAG) | 높음 (트리거 판정 + 오류 내성) |
| 실제 제품 범주 | 통화 분석 | Agent Assist |

##### C-5 상세 — 코어에 포함

통화에는 카드번호, 주민등록번호, 계좌번호가 섞인다. 이 시스템은 **실시간 자막을 화면에 띄우고 전사 결과를 DB에 저장**하므로, 마스킹이 없으면 설계 결함이다.

**파이프라인 — 정규화 단계가 정규식 앞에 온다**

```
STT 전사 결과
     ↓
[0] 한글 수사 정규화   ← rev.4 추가. 이 단계가 없으면 정규식이 무력화된다
     "구일공 일이삼일" → "910 1231"
     "공일공에 일이삼사" → "010 1234"
     ↓
[1] 정규식 탐지  (구조가 명확한 번호류: 주민번호·카드번호·계좌번호·전화번호)
     ↓
[2] NER 탐지     (이름·주소 등 구조가 없는 항목)
     ↓
[3] 마스킹 적용  ① 화면 자막 표시 전  ② PostgreSQL 저장 전 — 양쪽 모두
```

**왜 [0]단계가 필수인가**

4.2절이 지적하는 STT 오류 문제는 C-5에도 그대로 적용된다. 검색은 오류율 20%를 가정하면서 마스킹만 오류율 0%를 가정할 수는 없다.

| 실제 발화 | STT 결과 예시 | 정규화 없이 정규식 적용 시 |
|---|---|---|
| 010-1234-5678 | "공일공 일이삼사 오육칠팔" | **탐지 실패** |
| 010-1234-5678 | "010 1234 5678" | 하이픈 없음 → 패턴 보강 필요 |
| 910123-1234567 | "구일공일이삼 일이삼사오육칠" | **탐지 실패** |

| 항목 | 처리 |
|---|---|
| 탐지 방식 | **한글 수사 정규화** → 정규식 → NER |
| 적용 지점 | ① 화면 자막 표시 전 ② PostgreSQL 저장 전 — **양쪽 모두** |
| 원본 보관 | 하지 않음. 마스킹된 형태만 저장 |
| 착수 시점 | **3주차 — 자막 구현과 동시에** |
| 목표 | **문서에 정의된 패턴 목록에 대해 누락 0건** (아래 참조) |

**목표 재정의 — "누락 0건"의 범위를 명시한다**

무조건적인 "누락 0건"은 측정 자체가 성립하지 않는다. 실제 통화의 개인정보 발화 패턴을 확보할 수 없으므로, 팀이 만든 데이터로 평가하면 "우리가 상상한 패턴을 우리 정규식이 잡는다"는 순환 검증이 된다 — 5.5절이 F-1·G-1에 대해 지적한 것과 같은 구조다.

따라서 목표를 다음과 같이 한정한다.

> **정의된 패턴 목록**(주민등록번호, 카드번호, 계좌번호, 전화번호, 한글 수사 표기 변형)**에 대해 누락 0건.**
> 목록 밖 패턴에 대한 성능은 검증하지 않으며, 이를 문서에 명시한다.

**마스킹 재현율 곡선 — 4.2절 실험에 편입**

C-5의 성능도 STT 오류율에 따라 변한다. 4.2절 오류 주입 실험에 마스킹 재현율을 한 행 추가하면 측정 비용 없이 발표 소재가 하나 늘어난다. (4.2절 참조)

> 마스킹은 후순위 기능이 아니다. 자막을 띄우는 순간부터 필요하다.

| ① | 종결 사유를 뒷받침하는 기록이 없는데도 종결이 통과됨 | **가능** |
| ② | 처리 이력이 사후에 삭제·수정됨 | **가능** |
| ③ | 동일 대상의 반복 문의가 기존 종결 기록에 막혀 재검토되지 않음 | **가능** |
| — | 고의적 허위 기재 그 자체 | **불가능** |

> 이 문제 정의의 계기가 된 개별 보도는 **부록 D**로 분리했다. 본문·발표 자료에는 개별 사건의 시점·지역·경위를 쓰지 않는다. 참고하는 것은 **실패의 구조**뿐이다. (부록 A-4 원칙)

##### 도메인 — 코어와 통합한다 *(rev.4 핵심 변경)*

rev.3까지 F 모듈은 공공 실종신고 종결을 대상으로 했다. 이는 코어(A~E)와 **지식베이스·데이터 모델·화면이 완전히 이원화**되어 2주 이상의 오버헤드를 발생시킨다.

| 항목 | rev.3 (공공 실종신고) | **rev.4 (통신사 업무)** |
|---|---|---|
| 지식베이스 | 업무처리 규칙 — **별도 인덱스** | 약관 + 응대 매뉴얼 + 내부 처리 규정 — **코어와 동일 인덱스** |
| 데이터 모델 | 신고 사건 / 종결 사유 — **신규 테이블군** | **기존 call / 상담 이력 확장** |
| 화면 | 종결 입력 폼 — **신규 화면** | **기존 상담 이력 저장 폼에 검증 단계 삽입** |
| 추가 작업량 | 서브시스템 1개 분량 | 규정 인덱싱 + 요건 스키마 + 게이트 로직 |

**대상 업무 (택1 또는 2개)**

- **해지 방어 종결** — 해지 요청을 "고객이 유지 의사를 밝힘"으로 종결할 때
- **보상·환불 처리 종결** — 보상 요청을 "고객 동의로 종결"로 처리할 때

두 경우 모두 **근거 없이 사건을 닫는다**는 실패 구조가 동일하며, 지식베이스가 코어와 하나로 유지된다.

##### 주장 범위 — 반드시 지킬 것

이 모듈이 주장할 수 있는 것은 **"이런 일을 막습니다"가 아니다.**

> **"근거 없는 종결의 비용을 올린다."**

고의는 어떤 시스템도 막을 수 없다. 이 구분을 흐리면 프로젝트의 신뢰도가 떨어진다.

##### 기능 목록

| 기능 | 설명 | 채택 |
|---|---|---|
| F-1 | 고위험 건 자동 감지 → 에스컬레이션, 자동 종결 대상 제외 | 여유 시 (검증 불가) |
| **F-2** | **종결 요건 검증 게이트** — 종결 사유별 필수 근거 미기재 시 종결 차단 | **채택** |
| F-3 | 동일 고객 반복 문의 자동 연결 → 기존 종결 사유 재검증 요구 | 여유 시 |
| F-4 | **추가 전용(append-only) 감사 로그** — 삭제·수정 시도를 이벤트로 기록 | 채택 |

> **F-4 용어 정정 (rev.4)**: rev.3의 "불변 감사 로그"는 과장이다. PostgreSQL에서 완전한 불변성은 성립하지 않으며 DB 권한자는 레코드를 삭제할 수 있다. 부록 A-3(주장의 한계) 원칙을 문서 스스로 위반한 표현이었다.
> → **"추가 전용(append-only) 감사 로그"** 로 정정하고, **"완전한 불변성은 애플리케이션 레벨에서 보장할 수 없으며, 이 설계가 보장하는 것은 정상 경로를 통한 수정·삭제가 흔적을 남긴다는 것까지"** 라고 명시한다.

##### F-2 상세 — 이 모듈의 핵심

```
상담원이 "고객이 유지 의사를 밝힘" 사유로 해지 요청 종결 시도
        ↓
[RAG] 내부 처리 규정에서 해당 종결 사유의 요건 검색
        ↓
[규칙] 필수 근거 필드 충족 여부 판정
        ↓
┌─────────────────────────────────────┐
│ ⛔ 종결 요건 미충족                   │
│                                     │
│ 선택한 사유: 고객 유지 의사 확인       │
│ 필요 근거:                           │
│   ☐ 안내한 대체 요금제 또는 조건       │
│   ☐ 고객 확인 방법 (통화 시점)        │
│   ☐ 위약금 고지 여부                 │
│                                     │
│ 근거 3건 중 0건 미기재 → 종결 차단    │
│ 📄 근거 규정: 내부 처리 규정 제○조     │
└─────────────────────────────────────┘
```

**RAG의 역할이 여기서 달라진다.** A~E의 RAG는 "답을 찾아 사용자에게 보여주는" 역할이었다. F-2의 RAG는 **"행위를 검증하는 근거를 가져오는"** 역할이다. 검색 결과가 화면에 표시되는 정보가 아니라 게이트 판정의 입력이 된다.

판정 자체는 규칙으로 하고 LLM은 설명만 생성한다. 숫자와 판정을 모델에 맡기지 않는다.

**도메인을 옮겨도 이 서사는 유지된다.** 차별화 포인트는 "공공 도메인을 다뤘다"가 아니라 "RAG를 검증 도구로 썼다"이기 때문이다. 오히려 코어와 같은 인덱스를 쓰므로 **"하나의 지식베이스가 두 가지 방식으로 사용된다"**는 설명이 추가로 가능해진다.

##### 상용 제품 대비 위치

조사 결과, KT A'Cen 등 국내 AICC는 STT/TA 기반 **불완전판매 방지**(하면 안 되는 말 감지)를 제공한다. 그러나 **"근거 없이 사건을 닫는 것을 차단하는" 기능은 확인되지 않았다.** F-2가 이 프로젝트의 독자 영역이다.

#### G. 위기 상담 지원 *(선택 모듈 — 범위 엄격 제한)*

##### 배경

자살예방 상담전화 109는 상담 요청 급증으로 전체 전화의 절반가량만 응대하는 상황이 이어졌고, 정부는 2026년 상담 인력 증원과 야간 분담 체계를 발표했다. 특히 복지부는 **"AI를 활용한 상담일지 작성 및 위기 신호 조기 발굴을 통한 업무 부담 완화"**를 추진 과제로 직접 명시했다.

즉 이 모듈은 정부 보도자료가 필요하다고 적어둔 기능에 해당한다.

##### 절대 선 — 타협 불가

> **LLM이 위기 상황의 당사자와 직접 대화하게 만들지 않는다. 어떤 형태로도.**

자동 응답, 챗봇 대응, 초기 자동 분류 후 연결 — 전부 금지. 시스템은 **상담원을 돕는 도구로만** 존재한다.

##### 단방향 경고 원칙

> **시스템은 "위험 신호가 감지됐다"만 말한다. "안전하다"는 절대 말하지 않는다.**

- 위험도 점수(예: "위험도 78%")를 화면에 표시하지 않는다
- 낮은 점수는 상담원의 경계를 늦추게 만든다 — 오분류 비용이 극단적으로 비대칭인 도메인에서 이는 허용될 수 없다
- 신호가 있으면 프로토콜을 띄우고, 없으면 아무것도 하지 않는다
- UI에서 **침묵이 "이상 없음"으로 읽히지 않도록** 명시한다

##### 기능 목록

| 기능 | 설명 | 채택 |
|---|---|---|
| G-1 | 위기 대응 프로토콜 실시간 표시 (확인 항목 + 연계 절차) | 여유 시 |
| **G-2** | **지역 자원 연계 검색** — 주소지 기준 정신건강복지센터·자살예방센터 등 매칭 | **채택** |
| G-3 | 상담일지 자동 초안 (상담원 검토·수정 전제) | 여유 시 |
| G-4 | 상담원 소진 관리 — 고위험 통화 연속 배정 방지 | 여유 시 |

##### G-2를 채택하는 이유

109 상담에서 위험성이 높다고 판단되면 본인 동의를 받은 후 주소지 지역의 정신건강복지센터·자살예방센터로 연계되어 대면상담과 사례관리를 받게 된다. G-2는 이 연계 대상을 실시간으로 찾아주는 기능이다.

- **위험도 판정이라는 민감 영역을 우회한다** — 판정은 상담원이 하고, 시스템은 자원만 찾는다
- 전국 기관 목록·연락처·운영시간·관할은 **공개 데이터**라 구현과 검증이 모두 가능하다
- 지역·연령·상황 조건으로 기관을 추리는 것은 전형적인 조건 판정 + 검색 문제로, 기존 아키텍처와 정확히 맞는다
- 정답이 명확해서 **평가셋을 만들 수 있다** — **확장 모듈 중 유일하게 측정 가능한 앵커**다 (부록 B-3 참조)

##### 만들지 않는 것

- 자살 위험도 점수화 및 표시
- 위기자에 대한 자동 응답
- 위치 추적, 신고 자동화
- 실제 위기 상담 통화의 수집·녹음

## 3. 시스템 아키텍처

> **rev.4에서 변경 없음.** 구성요소와 데이터 흐름은 rev.3과 동일하다. F 모듈이 코어와 같은 Elasticsearch 인덱스·PostgreSQL 스키마를 쓰게 되면서, 오히려 rev.3보다 이 다이어그램에 더 정확히 들어맞는다.

```
[상담원 브라우저]
       │ React 대시보드
       │
   WebSocket (양방향)
       │
[Node.js 게이트웨이]
       │  - 오디오 청크 중계
       │  - 자막/카드/경고 푸시
       │
       ├──→ [Google STT] ──→ 부분 전사 결과
       │
       ▼
[FastAPI 코어]
       │
       ├─ 트리거 판정 모듈
       │     └─ 발화 완결성 / 침묵 길이 / 의도 신호
       │
       ├─ 검색 모듈 ──→ [Elasticsearch]
       │                  ├─ nori 형태소 (BM25)
       │                  ├─ dense_vector (임베딩)
       │                  └─ RRF 병합
       │
       ├─ 생성 모듈 ──→ [LLM] 근거 기반 요약
       │
       └─ 컴플라이언스 모듈 ──→ [분류기]
       │
       ▼
   [PostgreSQL] 통화 메타 / 상담 이력 / 평가 결과 / 감사 로그
```

### 3.1 도구 매핑 (투입자원 기준)

> **rev.4 변경**: 아래 표에 **새로 추가한 도구는 없다.** 생성 LLM은 위 다이어그램에 이미 있었으나 표에서 누락되어 있었고(레이턴시 예산 500ms·토큰 비용 지표가 근거를 잃는 상태였다), 캐시는 별도 저장소를 도입하지 않고 **애플리케이션 인메모리**로 확정했다.

| 항목 | 결정 사항 |
|---|---|
| 모델 | 상용 API / 오픈 모델 자체 호스팅 중 택1 |
| 실행 위치 | 외부 API인 경우 네트워크 왕복이 4.3절 예산에 포함됨 |
| 비용 | 통화당 토큰 비용 산정 기준 (6.1절 지표와 연결) |

> **폴백 모드는 리스크 대응이자 실험 조건이다.** "생성 없이 검색 결과만 보여줄 때와 생성 카드를 보여줄 때"를 비교하면 생성 단계의 기여도를 수치로 말할 수 있다.

> OpenCV는 억지로 끼워넣지 않는다. 투입자원 목록은 과정 전체 기준일 가능성이 높으며, 무리한 기능 추가는 프로젝트 완성도를 떨어뜨린다.

## 4. 핵심 기술 난제

### 4.1 트리거 판정 — 언제 검색할 것인가

일반 RAG는 완성된 질문을 받는다. 스트리밍은 다르다.

```
0.4초  "아"
0.9초  "아 저번에"
1.6초  "아 저번에 가입할"
2.4초  "아 저번에 가입할 때 6개월"
3.1초  "아 저번에 가입할 때 6개월 할인 된다고 했는데"
```

- **매 조각마다 검색** → 서버 과부하, 카드 깜빡임, 비용 폭증
- **너무 늦게 검색** → 대화가 이미 다음으로 넘어감

**검토할 트리거 전략**

| 전략 | 방법 | 예상 문제 |
|---|---|---|
| 침묵 기반 | N초 무음 시 검색 | 말이 느린 고객에서 지연 |
| 종결어미 기반 | "~요", "~까요", "~는데" 패턴 | 중간에 끊어 말하면 오발동 |
| 길이 기반 | 토큰 N개 누적 시 | 의미 무관하게 발동 |
| 분류기 기반 | 질문 완결 여부 판정 모델 | 학습 데이터 필요 |
| 하이브리드 | 위 조합 + 디바운싱 | 튜닝 복잡 |

**트리거 정답 정의 — 채점 코드가 성립하려면 필요하다** *(rev.4 추가)*

rev.3은 "적절 시점 발동률 ≥ 0.85"를 지표로 두었으나 **"적절한 시점"의 허용 오차가 정의되지 않아 규칙 기반 채점 코드를 작성할 수 없었다.**

```
골든셋의 각 시나리오는 정답 시점 t_gold 를 갖는다
  t_gold = 해당 질의 발화가 종료되는 시점(ms)

판정:
  t_gold - 300ms  ≤  t_fire  ≤  t_gold + 1,500ms   →  적절 발동
  t_fire < t_gold - 300ms                           →  조기 발동 (불필요 발동에 산입)
  t_fire > t_gold + 1,500ms                         →  지연 발동 (미발동으로 처리)
  발동 없음                                          →  미발동
```

- 하한 −300ms: 종결어미 기반 트리거가 발화 끝을 살짝 앞질러 발동하는 것은 허용
- 상한 +1,500ms: 이보다 늦으면 대화가 다음 주제로 넘어간 것으로 본다
- **이 두 값은 1주차 골든셋 스펙에 고정하고, 이후 임의로 바꾸지 않는다.** 기준을 바꿔가며 측정하면 지표가 무의미해진다

**측정 지표**: 적절 발동률, 발동 지연시간 분포, 불필요 발동률(조기 발동 포함)

### 4.2 STT 오류 내성 — 가장 중요한 실험

음성인식은 틀린다. 사람은 알아듣지만 검색은 실패한다.

| 실제 발화 | STT 결과 | 문제 |
|---|---|---|
| 해지 | 해제 | 완전히 다른 조항 검색 |
| 요금제 | 요금 제 | 띄어쓰기로 형태소 분해 실패 |
| 위약금 | 위약 금 | 동일 |
| 자동이체 | 자동 이체 | 동일 |
| 010-1234 | 공일공 일이삼사 | **C-5 마스킹 실패** |

**Elasticsearch가 여기서 필요해지는 이유**

```
1. nori 형태소 분석기 → 띄어쓰기 오류 흡수
2. 자모 분해 필터      → 유사 발음 오인식 대응
3. dense_vector 필드   → 의미 기반 검색
4. RRF 병합            → 위 3개 결과 통합
```

pgvector 대신 ES를 쓰는 근거가 여기서 생긴다. 한 엔진에서 형태소 검색과 벡터 검색을 동시에 처리할 수 있기 때문이다.

**대표 실험 (발표의 핵심 숫자)**

```
STT 오류율을 인위적으로 주입하며 측정

오류율        0%    5%    10%   15%   20%
────────────────────────────────────────
[검색 Recall@5]
BM25만        0.68  0.59  0.44  0.33  0.24
벡터만        0.71  0.66  0.48  0.39  0.31
하이브리드     0.79  0.74  0.66  0.58  0.49

[C-5 마스킹 재현율]   ← rev.4 추가
정규식만      1.00  0.83  0.71  0.60  0.52
정규화+정규식  1.00  0.97  0.94  0.90  0.86
```

> 위 수치는 예시 형식이며 실제 측정값으로 채워야 한다. **"오류율 10%에서 0.48 → 0.66으로 복구"** 형태의 문장 하나가 프로젝트 전체를 설명한다.
>
> 마스킹 행을 추가하는 비용은 오류 주입 스크립트를 그대로 재사용하므로 사실상 0에 가깝고, **"보안 기능도 같은 방식으로 측정했다"**는 서사가 하나 늘어난다.

**이 실험은 실제 음성 데이터 없이도 가능하다** *(rev.4 명시)*

오류 주입은 자모 치환·띄어쓰기 변형·동음이의 치환으로, 전부 **텍스트 레벨 조작**이다. 따라서 AI Hub 승인이 지연되어도 5주차 핵심 실험은 진행할 수 있다(11절 리스크 완화 요인).

동시에 정직하게 구분해야 할 것이 있다.

> 5.2절의 "실제 데이터로 검증한다"는 주장은 **STT 파이프라인 동작 검증과 데모**에 적용되며, **4.2절 오류 내성 실험은 합성 오류 기반**이다. 이 구분을 문서와 발표에 명시한다.

### 4.3 레이턴시 예산

통화는 기다려주지 않는다.

**두 지표를 분리해 측정한다** *(rev.4 변경)*

rev.3은 "트리거 발동 → 카드 표시"만 측정했다. 그러나 상담원이 체감하는 것은 "고객이 말을 마침 → 카드가 뜸"이다. STT 지연을 예산 밖에 둔 정의는 유리하게 잡힌 것이다.

| 지표 | 구간 | 목표 |
|---|---|---|
| **내부 처리 지연** | 트리거 발동 → 카드 표시 | **p95 ≤ 1,000ms** |
| **체감 지연 (End-to-End)** | 발화 종료 → 카드 표시 | **측정·기록** (목표 미설정) |

체감 지연에는 다음이 포함되며, 이는 팀이 통제할 수 없는 구간이다.

- Google STT 부분 결과 반환 지연
- Node.js 게이트웨이 ↔ FastAPI 홉
- 브라우저 렌더링

> 통제 가능한 구간과 아닌 구간을 분리해 둘 다 측정한다는 것 자체가 설계 성숙도의 근거가 된다. 목표를 낮추는 것이 아니라 **측정 범위를 정직하게 넓히는 것**이다.

**내부 처리 예산 (합계 910ms, 여유 90ms)**

| 단계 | 목표 | 최적화 수단 |
|---|---|---|
| 트리거 판정 | 10ms | 규칙 우선, 모델은 캐싱 |
| 검색 | 150ms | 인덱스 워밍업, 필드 최소화 |
| 리랭킹 | 200ms | 상위 20개만, 배치 추론 |
| 생성 | 500ms | 스트리밍 출력, 프롬프트 캐싱 |
| 전송 | 50ms | WebSocket 유지 연결 |

> **생성 500ms의 전제**: 외부 API를 사용할 경우 이 값은 **스트리밍 첫 토큰 기준**이며, 카드 전체 완성 기준으로는 초과할 가능성이 높다. 1주차 LLM 확정 시 실측하고, 초과하면 3.1절의 **폴백 모드(검색 스니펫만 표시)**를 기본값으로 두는 것을 검토한다.

**추가 전략**: 자주 나오는 질문의 검색 결과 캐싱(인메모리), 통화 시작 시 고객 정보 기반 사전 인덱싱

## 5. 데이터 확보 계획

### 5.1 지식베이스 (검색 대상 문서)

조건이 복잡해서 실제로 검색이 어려운 문서를 골라야 한다.

| 후보 | 장점 | 단점 |
|---|---|---|
| 통신사 요금제 약관 | 공개, 조건 복잡, 문의 유형 다양 | 분량 방대 |
| 보험 약관 | 조건 중첩 극심, 컴플라이언스 이슈 풍부 | 전문용어 장벽 |
| 카드 혜택 조건 | 실적 조건 등 판정 난이도 높음 | 갱신 빈번 |

**권장**: 통신사 요금제 약관 + 응대 매뉴얼(직접 작성) + **내부 처리 규정(직접 작성 — F-2용)**. 팀원 모두가 도메인을 이해하므로 라벨링이 빠르다.

**하나의 인덱스, 두 가지 용도** *(rev.4)*

```
[Elasticsearch 단일 인덱스]
   ├─ 요금제 약관          → B (상담원에게 답을 보여줌)
   ├─ 응대 매뉴얼          → B
   └─ 내부 처리 규정       → F-2 (게이트 판정의 근거를 가져옴)
```

F-2의 도메인을 통신사로 옮긴 결과, **별도 인덱스가 필요 없어졌다.** 같은 검색 파이프라인이 두 가지 역할을 수행하는 구조가 되며, 이것이 10.6의 근거를 오히려 강화한다.

> 약관 원문 전재는 저작권 문제가 될 수 있다. 검색 인덱스 내부 저장은 문제없으나, 화면 표시는 요약·해석 중심으로 하고 출처를 명시한다.

### 5.3 골든셋 구축 *(rev.4 일정 조정)*

**순환 의존을 해소한다.** 골든셋의 정답 라벨은 "이 시점에 표시되어야 할 문서 ID"이므로, **문서 수집 → 청킹 → ID 부여가 선행되어야 한다.** rev.3은 1주차에 문서 수집과 골든셋 50개를 병렬 배치했으나 이는 물리적으로 불가능하다.

| 주차 | 골든셋 | 전제 |
|---|---|---|
| 1주차 | **10~20개** | 문서 수집 + 청킹 + ID 부여 완료 후 |
| 2주차 | **50개** | 베이스라인 측정은 10~20개로 시작 가능 |
| 3주차 | **150개** | — |

```
각 시나리오마다:
  - 고객 발화 스크립트
  - 정답 시점 t_gold (발화 종료 시점, ms)      ← 4.1절 트리거 채점용
  - "이 시점에 표시되어야 할 문서 ID" (정답 라벨)
  - 표시되면 안 되는 문서 ID (오답 후보)
  - 컴플라이언스 위반 삽입 여부
  - 개인정보 패턴 삽입 여부 및 표기 형태        ← C-5 채점용 (숫자 / 한글 수사)

음성 확보:
  1순위 - AI Hub 데이터에서 유사 시나리오 매칭
  2순위 - TTS 합성 (승인 지연 시 대비책)

STT 오류 주입:
  프로그램으로 자모 치환 / 띄어쓰기 변형 / 동음이의 치환 / 숫자→한글 수사 변환
  → 오류율 0~20% 구간별 성능 곡선 생성 (검색 + 마스킹)
```

> **소규모 셋의 통계적 한계를 명시한다.** 10~20개 골든셋의 Recall@5는 신뢰구간이 넓다. 2주차 베이스라인은 **"방향을 확인하는 값"**이며, 정식 기준선은 50개 이상 확보 후 재측정하여 고정한다.

### 5.4 F·G 모듈 데이터 *(rev.4 갱신)*

| 모듈 | 필요 데이터 | 확보 가능성 |
|---|---|---|
| **F-2** | **종결 사유별 요건이 명시된 내부 처리 규정** | **가능 — 팀이 직접 작성. 코어 지식베이스에 통합** |
| F-3 | 반복 문의 판정용 가상 상담 이력 | 가능 — 합성 데이터로 구성 |
| G-2 | 전국 정신건강복지센터·자살예방센터 목록 | 가능 — 공개 데이터 |
| C-5 | 개인정보 패턴이 포함된 발화 시나리오 | 가능 — 팀 작성 (단 5.5절 한계 적용) |
| F-1 / G-1 | 실제 고위험 통화 | **불가능** |

> **F-2 데이터가 rev.3보다 쉬워졌다.** 공공 업무처리 규칙을 찾아 인덱싱할 필요가 없고, 응대 매뉴얼을 작성하면서 종결 요건 조항을 함께 쓰면 된다. 다만 이 경우 "우리가 만든 규정을 우리가 검증한다"는 성격이 있으므로, **규정 문서의 형식과 조항 구조를 실제 통신사 약관 체계에 맞춰 작성**하고 그 사실을 명시한다.

### 5.5 데이터 한계 — 반드시 명시할 것

**탐지 성능을 검증할 수 없는 기능이 있다.**

| 기능 | 검증 가능성 | 사유 |
|---|---|---|
| F-1 고위험 건 감지 | **불가** | 실제 데이터 없음 |
| G-1 프로토콜 판정 | **불가** | 동일 |
| **C-5 목록 밖 패턴** | **불가** | 실제 통화의 개인정보 발화 패턴 확보 불가 |
| C-5 정의된 패턴 목록 | 가능 | 패턴을 문서에 명시했으므로 측정 성립 |
| G-2 자원 매칭 | 가능 | 공개 데이터로 정답 확인 |
| F-2 요건 판정 | 가능 | 규칙 기반 판정이므로 결정론적 |

- 실제 위기 상담 음성·기록은 확보할 수 없고, 확보하려 시도해서도 안 된다
- AI Hub 감정 데이터는 위기 상담이 아니다
- 공개된 한국어 심리상담 데이터셋 중 일부(예: CounselGPT)는 질의·답변이 전량 LLM API로 생성된 것이라 실제 위기 발화 패턴이 아니다
- 팀이 직접 작성한 시나리오로 평가하면 **"우리가 상상한 표현을 우리 모델이 잡는다"**는 순환 검증이 된다 — **이는 C-5에도 동일하게 적용된다**

따라서 문서와 발표에 다음을 명시한다.

> **탐지 성능은 검증되지 않았으며, 이 시스템은 상담원의 판단을 대체하지 않는다.**
> **C-5 마스킹은 문서에 정의된 패턴 목록에 한해 검증되었으며, 목록 밖 패턴의 누락 가능성은 배제할 수 없다.**

이 한계를 숨기지 않고 적는 것이 프로젝트의 신뢰도를 높인다. 검증되지 않은 것을 검증된 것처럼 제시하는 것이 이 도메인에서 가장 위험한 실수다.

## 6. 평가 설계

### 6.1 지표

| 영역 | 지표 | 목표 기준선 |
|---|---|---|
| 검색 | Recall@5 | ≥ 0.70 (오류 없음) / ≥ 0.60 (오류 10%) |
| 검색 | MRR | ≥ 0.55 |
| 트리거 | 적절 발동률 (4.1절 허용 구간 기준) | ≥ 0.85 |
| 트리거 | 불필요 발동률 (조기 발동 포함) | ≤ 0.15 |
| 생성 | 환각 수치 발생 | 150문항 중 5건 이하 |
| 생성 | 출처 표시율 | 100% |
| 컴플라이언스 | 재현율 | ≥ 0.90 (누락이 오탐보다 위험) |
| 컴플라이언스 | 정밀도 | ≥ 0.60 (경고 피로 방지) |
| **C-5** | **정의된 패턴 목록에 대한 마스킹 누락** | **0건 — 절대 규칙** |
| C-5 | 과잉 마스킹률 (일반 숫자 오탐) | ≤ 0.05 |
| C-5 | 오류율 10%에서의 마스킹 재현율 | ≥ 0.90 |
| 성능 | **내부 처리** p95 레이턴시 | ≤ 1,000ms |
| 성능 | **체감(E2E)** p95 레이턴시 | 측정·기록 (목표 미설정) |
| 성능 | 통화당 토큰 비용 | 측정·기록 |
| **F-2** | 종결 요건 판정 정확도 | **100% — 타협 없는 절대 규칙** |
| F-2 | 근거 규정 검색 정확도 | ≥ 0.90 |
| F-3 | 반복 문의 연결 재현율 | ≥ 0.95 *(여유 시 착수 — 미구현 시 N/A)* |
| **G-2** | 자원 매칭 정확도 (관할·운영시간 기준) | ≥ 0.95 |
| G-2 | 폐지·이전 기관 반환 건수 | **0건** |
| F-1 / G-1 | 탐지 성능 | **측정 불가 — 5.5절 참조** |

> **H·I 지표에 관하여**: 부록 B의 H·I는 착수가 확정되지 않았으므로 본 표에 넣지 않는다. **착수가 확정되는 시점에 부록 B의 지표를 이 표로 편입**하며, 그전까지는 부록에만 둔다. 미착수 기능의 지표를 본 표에 두면 평가 설계의 일관성이 깨진다.

### 6.2 채점 원칙

1. **LLM을 채점자로 쓰지 않는다.** 답을 만든 모델이 자기 답을 심판하면 순환이 된다. 모든 지표를 규칙으로 계산해 재현 가능하게 한다.
2. **여러 번 실행한 값 중 최저치를 기준선으로 고정한다.** 생성 모델은 같은 입력에도 답이 달라진다.
3. **기준선 미달 시 CI 실패**로 처리한다. 개선이 아니라 회귀 방지가 목적이다.
4. **C-5·F·G의 절대 규칙은 1건이라도 뚫리면 실패로 처리한다.** 마스킹 누락, 종결 요건 판정, 폐지 기관 반환 등은 평균값으로 평가하지 않는다.
5. **채점 파라미터는 1주차에 고정한다.** 트리거 허용 구간(−300ms / +1,500ms), C-5 패턴 목록 등은 측정 중에 변경하지 않는다.

### 7.1 인터페이스 계약 우선

1주차에 모듈 간 스키마를 확정한다. 이것이 병렬 작업의 전제 조건이다.

```json
// 전사 이벤트
{
  "call_id": "c_001",
  "speaker": "customer",
  "text": "6개월 할인 된다고 했는데",
  "text_masked": "6개월 할인 된다고 했는데",
  "is_final": true,
  "timestamp_ms": 3100
}

// 추천 카드
{
  "call_id": "c_001",
  "trigger_at_ms": 3150,
  "cards": [
    {
      "title": "프로모션 할인 적용 시점 안내",
      "summary": "신규 가입 할인은 가입 다음 달 청구서부터 반영됩니다.",
      "source": {"doc": "요금제약관", "clause": "3.2"},
      "score": 0.87
    }
  ],
  "latency_internal_ms": 780,
  "latency_e2e_ms": 1420
}

// 종결 검증 결과 (F-2)
{
  "call_id": "c_001",
  "close_reason": "고객 유지 의사 확인",
  "passed": false,
  "required": [
    {"field": "alt_plan_offered", "filled": false},
    {"field": "confirm_method",   "filled": false},
    {"field": "penalty_notified", "filled": false}
  ],
  "source": {"doc": "내부처리규정", "clause": "5.1"}
}
```

> **전사 이벤트에 `text_masked`가 추가되었다.** C-5가 코어이므로 스키마 단계에서 마스킹 결과를 명시적으로 실어 나른다. 화면과 DB는 이 필드를 사용한다.

### 7.2 평가 하네스는 1주차에, 그리고 손을 뗀다

프로젝트 리드가 평가 하네스와 CI를 먼저 깔고 이후 모듈 개발은 팀원에게 넘긴다.

- 팀원이 각자 모듈을 고칠 때마다 숫자가 자동으로 나온다
- "제 방식이 더 나은 것 같은데요" 같은 논쟁이 측정으로 대체된다
- 면접에서 **"팀의 품질 기준을 설계했다"**는 서사가 된다

## 10. 차별화 포인트

발표와 면접에서 강조할 순서.

### 10.1 "통화 중"에 개입한다

대부분의 콜센터 프로젝트는 통화 후 녹음을 처리한다. 실시간 개입은 트리거 판정, 오류 내성, 레이턴시 예산이라는 별개의 문제군을 만든다.

### 10.2 STT 오류율별 성능 곡선

> "오류율 10%에서 Recall@5가 0.48까지 떨어졌고, 하이브리드 검색으로 0.66까지 복구했습니다."

이 실험을 해본 지원자는 드물다. 검색 품질을 **측정하고 개선한** 증거다.

### 10.3 보안 기능도 같은 방식으로 측정했다 *(rev.4 추가)*

> "마스킹도 STT 오류에 취약합니다. 정규식만으로는 오류율 10%에서 재현율이 0.71이었고, 한글 수사 정규화를 앞에 붙여 0.94까지 올렸습니다."

대부분의 프로젝트는 마스킹을 "정규식 붙였다"로 끝낸다. **입력이 STT 결과라는 점이 마스킹 설계를 바꾼다**는 것을 인지하고 측정까지 한 것은 드문 접근이다.

### 10.4 채점에 LLM을 쓰지 않는다

답을 만든 모델이 자기 답을 심판하면 순환이 된다. 모든 지표를 규칙으로 계산해 재현 가능하게 했다.

### 10.5 재현율 우선 설계의 근거

컴플라이언스 감지에서 누락(false negative)이 오탐보다 위험하다는 비대칭을 지표에 반영했다.

### 10.6 RAG를 검증 도구로 쓴다 (F-2)

일반적인 RAG는 답을 찾아 보여준다. F-2의 RAG는 **행위를 차단할 근거를 가져온다.** 검색 결과가 사용자에게 보여지는 정보가 아니라 게이트 판정의 입력이 되는 구조는 흔하지 않다.

> **rev.4에서 이 서사가 더 강해졌다.** F-2를 코어와 같은 인덱스로 옮기면서 **"하나의 지식베이스가 두 가지 방식으로 소비된다"**는 설명이 가능해졌다. 별도 시스템을 하나 더 만든 것이 아니라, 같은 검색 파이프라인의 출력을 사람에게 보여줄 것인가 게이트에 넣을 것인가의 차이라는 점을 다이어그램 하나로 설명할 수 있다.

### 10.7 측정 범위를 정직하게 넓혔다 *(rev.4 추가)*

> "내부 처리는 p95 900ms를 맞췄지만, 상담원이 체감하는 발화 종료부터 카드 표시까지는 1.4초입니다. STT 반환 지연이 대부분이고, 그건 저희가 통제할 수 없는 구간입니다."

목표 구간만 측정하고 유리한 숫자를 말하는 것보다, 통제 가능/불가능 구간을 분리해 둘 다 제시하는 쪽이 신뢰를 얻는다.

### 10.8 단방향 경고 원칙 (G)

> "시스템은 위험 신호가 감지됐다만 말하고, 안전하다는 절대 말하지 않습니다."

시스템의 발언 범위를 스스로 제한한 설계다.

### 10.9 검증 불가를 명시한다

F-1·G-1의 탐지 성능, C-5의 목록 밖 패턴은 측정할 수 없다고 문서에 적는다. 자기 프로젝트의 미검증 영역을 스스로 표시하는 것은 과장된 주장보다 훨씬 강한 인상을 남긴다.

### 10.10 실패 사례 분석

"이런 질문은 여전히 틀리고, 원인은 이것이며, 해결하려면 이런 접근이 필요하다." 이 섹션의 존재 자체가 프로젝트 성숙도를 보여준다.

- **LLM은 설명만 한다.** 판정 결과를 사람이 읽을 문장으로 옮기는 역할
- 숫자와 판정을 생성 모델에 맡기지 않는다

| 쓰지 않을 표현 | 대신 쓸 표현 |
|---|---|

### A-4. 발표·시연 시 주의

- 개별 사건의 실명, 지역, 세부 정황을 쓰지 않는다. **관련 자료는 부록 D에만 두고 외부 배포본에서 제거한다**
- 문제 정의는 사건이 아니라 **일반적 실패 유형**으로 서술한다 — "종결 사유의 근거가 검증되지 않는 문제"
- 위기 통화를 재현하는 데모는 하지 않는다. 프로토콜 표시 화면과 자원 검색 결과만 시연한다
- 자살 관련 내용은 자살예방 보도준칙을 참고해 표현을 다듬는다. 구체적 방법·장소 묘사는 넣지 않는다
- 발표 자료 말미에 상담 안내를 넣는다: **자살예방 상담전화 109 (24시간)**

### A-5. 데이터 취급

- 실제 위기 상담 음성·기록을 수집하지 않는다
- 시연·평가용 시나리오는 팀이 직접 작성한 가상 사례만 사용한다
- 가상 사례에도 실제 인물을 연상시키는 정보를 넣지 않는다
- **C-5 평가용 개인정보 패턴은 전부 가상 번호를 사용한다.** 실제 유효한 번호 형식을 피한다

## 부록 B — 추가 검토 모듈 (H·I)

**코어(A~E) 완료 후 여유가 있을 때 둘 중 하나만** 착수한다. 착수가 확정되면 아래 지표를 6.1절 표로 편입한다.

### B-0. 검토 결론 요약

| 제안 | 판단 | 사유 |
|---|---|---|
| C-5 개인정보 마스킹 | **채택, 코어로 상향** | 기존 명세의 실제 누락. 2.2절 반영 완료 |
| 탐지 실패 로그 → 개선 루프 | **채택** | 추가 비용 거의 없음. D-4 확장으로 반영 완료 |
| I 모듈 (이상거래 게이트) | 조건부 채택 | H·I 중 택1이라면 I를 권장 |
| H 모듈 (악성민원 대응) | 조건부 채택 (범위 축소 전제) | H-4·H-5는 축소 또는 제외 |
| G-2를 H·I로 대체 | **기각** | B-3 참조 |

### B-1. 모듈 I — 이상거래·본인확인 게이트 *(H·I 중 권장)*

**주장 범위**: "본인확인 없는 민감 요청 처리의 비용을 올린다." — "보이스피싱을 막습니다"가 아니다.

F-2와 구조가 1:1로 대응된다. 규정 문서만 바뀌고 흐름은 동일하다.

```
상담원이 계좌 정보 변경 / 명의 변경 등 민감 요청 처리 시도
        ↓
[RAG] 보안수칙에서 해당 요청 유형의 필수 확인 절차 검색
        ↓
[규칙] 필수 확인 항목 충족 여부 판정
        ↓
┌─────────────────────────────────────┐
│ ⚠ 본인확인 요건 미충족                │
│ 요청 유형: 계좌 정보 변경             │
│ 필요 확인:                           │
│   ☐ 등록 연락처 통한 재확인          │
│   ☐ 추가 인증수단 확인               │
│   ☐ 요청 경위 기록                   │
│ 근거 3건 중 0건 → 처리 보류 권장      │
│ 📄 근거: ○○ 보안수칙 제○조            │
└─────────────────────────────────────┘
```

| 기능 | 설명 | 채택 |
|---|---|---|
| I-1 | 고위험 요청 패턴 탐지 | 여유 시 (검증 불가) |
| **I-2** | 본인확인 요건 검증 게이트 | 권장 |
| I-3 | 공개 사기 화법 사례와 유사도 매칭 → **경고 카드만, 자동 차단 없음** | 여유 시 |
| I-4 | 통화 후 의심 플래그 집계 | 여유 시 |

**지표 (착수 확정 시 6.1절로 편입)**

| 지표 | 목표 |
|---|---|
| I-2 확인 요건 판정 정확도 | 100% — F-2와 동일한 절대 규칙 |
| I-2 근거 규정 검색 정확도 | ≥ 0.90 |
| I-1 탐지 재현율 | 측정 불가 |

**발언 범위** (부록 A-1 확장)

| 할 수 있는 말 | 하면 안 되는 말 |
|---|---|
| "이 요청 유형은 확인 항목 3건이 필요합니다" | "이 사람은 사기범입니다" |
| "유사 사기 화법 패턴이 감지되었습니다" | "이 통화는 안전합니다" |
| "관련 보안수칙은 다음과 같습니다" | "이 거래는 처리해도 됩니다" |

**한계 명시**: 실제 사기 통화 데이터는 확보하지 않는다. I-1의 탐지 성능은 F-1·G-1과 동일하게 검증 불가다. 금융감독원·경찰청이 공개한 사기 유형별 화법 사례는 **규정 문서처럼 인덱싱하여 I-2·I-3의 RAG 근거로만** 쓴다.

### B-2. 모듈 H — 악성민원 대응 *(범위 축소 전제)*

**주장 범위**: "폭언 노출을 기록하고 대응을 돕는다." — "감정노동을 없앤다"가 아니다.

| 기능 | 설명 | 채택 |
|---|---|---|
| H-1 | 고객 채널 대상 폭언·욕설 실시간 탐지 | 가능 |
| H-2 | 상담원용 대응 문구 카드 | 가능 (B-4 재사용) |
| H-3 | 통화 종료 시 고위험 민원 태깅 | 가능 (D-2·D-3 확장) |
| H-4 | 상담원별 누적 노출 지표 | **축소 또는 제외** |
| H-5 | 임계치 초과 시 관리자 알림 | **직전 1건 기반으로 축소** |

#### H-1의 데이터 — 재사용 범위를 정확히 한다

"C모듈과 동일한 분류기, 대상 채널만 상담원 → 고객으로 전환"은 부정확하다. **아키텍처는 재사용되지만 모델은 새로 학습해야 한다.** C모듈은 확정적 보장 표현·개인정보 요구를 잡는 라벨셋이고, H-1은 폭언·욕설·성희롱이다. 라벨, 학습 데이터, 평가셋이 모두 다르다.

AI Hub 「고객 응대 음성」의 감정 태깅을 근거로 "검증 가능"이라고 보는 것도 낙관적이다. **감정 라벨과 폭언 라벨은 다르다.** 화난 고객이 모두 폭언을 하지 않고, 차분한 어조의 성희롱도 있다.

> H-1의 출발점은 AI Hub 감정 태깅이 아니라 **혐오표현 멀티라벨 데이터셋(Unsmile 계열)** 기반 분류기다. KcELECTRA + Unsmile 파인튜닝이 정확한 출발점이며, 별도 학습과 평가셋이 필요하다. macro-F1으로 평가하되, 클래스 불균형이 크므로 정확도는 쓰지 않는다.

#### H-4 / H-5를 축소하는 이유

**상담원별 누적 지표는 직원 감시 도구가 될 수 있다.** 보호 목적으로 설계해도 조직에 들어가면 성과 평가로 전용되는 것이 이 종류 데이터의 전형적 경로이며, 학생 프로젝트에는 이를 통제할 거버넌스가 없다.

산업안전보건법이 사업주에게 감정노동자 보호 조치를 요구하는 취지는 정당하다. 그러나 **"누가 얼마나 폭언에 노출됐는지"를 개인 단위로 기록·보관하는 시스템**을 만드는 것은 별개 문제다.

권장 형태 (아래로 갈수록 안전)

1. **집계는 팀·시간대 단위로만** — "야간 시간대 고위험 통화 비율"
2. 개인별 지표를 만든다면 **본인만 열람 가능**, 관리자에게 미노출
3. **H-5는 개인 이력이 아니라 직전 통화 1건만 보고 판정** — 누적 기록 없이 목적 달성. 저장할 데이터가 없어지므로 가장 깔끔하다

**3번을 권장한다.**

### B-3. G-2 대체 제안을 기각하는 이유

"G-2는 전형적인 조건 매칭 문제라 기술적 차별점이 작다"는 이유로 H 또는 I로 대체하자는 제안이 있었으나, 이는 G-2를 채택한 이유를 반대로 읽은 것이다.

| 기능 | 탐지·판정 성능 검증 |
|---|---|
| F-1 고위험 건 감지 | 불가 (실제 데이터 없음) |
| G-1 프로토콜 판정 | 불가 |
| H-1 폭언 탐지 | 부분 가능 (분포 괴리 존재) |
| I-1 이상 패턴 탐지 | 불가 |
| **G-2 자원 매칭** | **가능 — 공개 데이터로 정답 확인** |

G-2는 관할이 맞는지, 운영시간이 맞는지, 폐지된 기관을 반환하지 않는지를 전부 검증할 수 있다. **기술적으로 화려하지 않은 것이 아니라, 확장 모듈 중 유일하게 측정 가능한 앵커다.**

G-2를 빼면 확장 모듈 전체에서 수치로 제시할 수 있는 지표가 사라진다. 발표에서 "이것도 못 재고 저것도 못 잽니다"가 되는 순간 F·G·H·I 전부의 설득력이 함께 무너진다.

덧붙여 I-2는 F-2와 같은 패턴의 두 번째 인스턴스이므로, **재사용성 입증 외에 새로 증명되는 것이 적다.** 이것이 I를 "여유 시"로 두는 이유이기도 하다.

### B-4. H·I 관련 리스크

| 리스크 | 대응 |
|---|---|
| H-4·H-5가 감시 도구로 전용 | 개인 단위 누적 저장을 하지 않는 설계(B-2 3번) 채택 |
| H-1을 C모듈 재사용으로 오해 | 별도 학습·평가셋 필요를 문서에 명시 |
| I-3이 자동 차단으로 오해 | "경고 카드만, 판단은 상담원" 반복 명시 |
| H·I 동시 착수로 코어 부실화 | **둘 다 하지 않는다. 택1, 그것도 여유 시** |
