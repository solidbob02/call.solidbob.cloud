# 021. RRF 순위 병합을 ES 가 아니라 `ai/` 코드에서 계산한다

- **날짜**: 2026-08-27
- **상태**: 채택 · **병합 함수 구현 완료** (2026-08-27, `ai/apps/retrieval/domain/services/fusion.py`)
  — 배선은 4주차 하이브리드 검색에서. 지금은 BM25 단독이라 병합할 순위가 하나뿐이다
- **관련**: `jekyll/_backlogs/w2-naive-rag.md`, `_project/decisions/017`(ES 인덱스),
  [3.1절 기술 스택](/docs/03/), 8주 로드맵 4주차

## 맥락

기획서 3.1절이 검색을 **`nori(BM25) + dense_vector + RRF`** 로 지정했다. 그런데 2026-08-27
장민석이 실측한 결과 **RRF 만 유료 기능**이었다.

```
403 current license is non-compliant for [Reciprocal Rank Fusion (RRF)]
```

**8.15.3 과 9.5.1 양쪽 다** basic 라이선스에서 거부된다 — 버전을 올려도 해결되지 않는다.
`retriever.rrf` 는 Elastic 의 상용 구독 기능이다.

**막힌 것은 순위 병합 한 가지뿐이다.** BM25 · kNN · nori · `dense_vector` · `collapse` 는
basic 에서 전부 된다.

## 선택지

| 안 | 비용 | 문제 |

| A. 30일 trial | 무료 | **만료 2026-09-26 → 프로젝트 종료(10-27)를 못 넘긴다.** 클러스터당 1회뿐이라 되돌릴 수도 없다. 발표 시연 중 만료되면 그대로 죽는다 |

| C. `bool` `should` 로 점수를 더한다 | 무료 | **틀린 방법이다.** BM25 점수(무한대 범위)와 코사인 유사도(0~1)는 스케일이 달라 그냥 더하면 한쪽이 지배한다. RRF 가 존재하는 이유가 이것이다 |
| E. LangChain `EnsembleRetriever` | 무료 | 아래 별도 절 — **가능하지만 이 함수에는 손해다** |
| **D. `ai/` 검색 코드에서 RRF 를 계산한다** | 무료 | 코드가 몇 줄 는다 |

### E 를 따로 보는 이유 — 랭체인은 라이선스를 피해 가는 길이 아니다

`EnsembleRetriever` 가 하는 일이 정확히 **weighted RRF** 다(`weights` + `c`, 기본 60,
`weighted_reciprocal_rank()`). 즉 D 와 **같은 알고리즘을 같은 위치(파이썬 클라이언트)에서**
돌린다. 막힌 것은 ES 서버가 대신 계산해 주는 기능이지 알고리즘이 아니므로, 랭체인이 무언가를
뚫어 주는 게 아니다. 그 위에서 이 저장소에는 세 가지가 걸린다.

1. **`ai/CLAUDE.md` 절대 지킬 것 4번이 "랭킹 산식은 순수 파이썬"이라고 못박고 있다.**
   `.importlinter` 계약 3 이 `retrieval.domain`·`evaluation` 에서 `langchain` import 를 금지해
   이를 구조로 강제한다. 랭체인을 쓰면 병합 로직이 `domain/` 에 못 있고 `adapter/` 로 밀린다.
2. **글루 코드가 절약분보다 크다.** `EnsembleRetriever` 는 `BaseRetriever`·`Document` 를 다루고
   우리는 `RetrievalPort`·`RetrievedDoc` 를 쓴다 — 래퍼 2개와 변환 4번이 필요하다.
   아끼려는 코드가 10줄인데 붙이는 코드가 더 길다.
3. **`_msearch` 왕복 1회가 2회가 된다.** 우리는 *같은 인덱스*에 BM25·kNN 두 질의를 던지는
   것이라 한 번에 보낼 수 있는데, `EnsembleRetriever` 는 독립적인 retriever 들을 합치는
   구조라 각자 왕복한다. 7.3절 내부 처리 p95 ≤1,000ms 를 생각하면 늘릴 이유가 없다.

**다시 볼 조건**: 병합 대상이 3개 이상으로 늘거나(BM25 + dense + sparse + 리랭커) 가중치
관리가 실제로 부담이 될 때. 그리고 **랭체인이 제값을 하는 자리는 따로 있다** — `ai/CLAUDE.md`
예정 목록의 `orchestration`(랭그래프 파이프라인)이다. **파이프라인에는 쓰고 랭킹 산식에는
쓰지 않는다**가 경계다.

## 결정

**D.** 하이브리드 검색(4주차)에서 BM25 와 kNN 을 각각 질의하고, **순위 병합은 `ai/` 에서** 한다.

```python
def rrf(rankings: list[list[str]], k: int = 60) -> list[str]:
    """RRF — 순위의 역수 합. 점수 스케일이 달라도 되는 이유가 이것이다."""
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.__getitem__, reverse=True)
```

두 질의는 `_msearch` 로 한 번에 보내 왕복을 하나로 줄인다.

**2026-08-27 구현됨** — `retrieval/domain/services/fusion.py` 의
`reciprocal_rank_fusion()` / `fuse_ids()`. `ai/CLAUDE.md` 4번대로 `domain/` 에 두었고
단위 테스트 14건으로 고정했다. 구현하면서 정한 규칙 셋:

- **한 순위 안의 중복은 한 번만 센다** — 쪼개진 청크가 같은 조항으로 두 번 올라와도
  그 조항만 부당하게 유리해지면 안 된다
- **동점은 `doc_id` 오름차순으로 가른다** — 실행마다 순서가 달라지면 채점이 흔들린다(절대 원칙 1)
- **빈 순위는 건너뛴다** — 그 검색이 결과를 못 냈다는 뜻이지 오류가 아니다

## 근거

**이건 우회가 아니라 이 프로젝트에는 오히려 맞는 방향이다.**

1. **RRF 는 원래 이게 전부다.** 순위의 역수 합이고 `k` 는 관례적으로 60이다. 라이선스가
   막고 있는 것은 알고리즘이 아니라 그 알고리즘을 서버에서 실행해 주는 편의다.
2. **평가 하네스가 채점할 수 있게 된다.** 병합이 우리 코드 안에 있으면 단위 테스트로 고정되고
   `k` 를 바꿔 가며 Recall@5 변화를 잴 수 있다. ES 안에 있으면 블랙박스다 —
   "판정은 규칙이" (절대 원칙 9), "재현 가능해야 한다" (절대 원칙 1) 와 같은 방향이다.
3. **엔진 교체 위험이 사라진다.** 4주차에 검색 품질을 올리는 게 목표인데, 그 주에 엔진을
   갈아끼우면 개선 폭을 무엇의 공으로 돌릴지 알 수 없게 된다.
4. **발표 중에 만료되지 않는다.** trial 은 2026-09-26 에 끝나고 프로젝트는 10-27 까지다.

## 주의

- **`k` 를 측정 없이 바꾸지 않는다.** 60은 관례값이고 우리 데이터에서 검증한 값이 아니다.
  4주차에 하이브리드를 붙일 때 `k` 도 함께 재고, 그 전에는 60으로 둔다 — 지금 이 문서에
  "60이 최적"이라고 쓰지 않는다(절대 원칙 2).
- 이 결정은 **4주차용**이다. 2주차 베이스라인(`w2-naive-rag`)은 BM25 단독이라 병합이 없다.
- 기획서 3.1절의 "RRF" 표기는 그대로 유효하다 — 알고리즘은 같고 실행 위치만 다르다.
  다만 3.1절에 "ES 의 RRF 기능"으로 읽힐 여지가 있다면 그 표현만 손본다.

## 되돌리는 법

Elastic 유료 구독을 얻으면 `retriever.rrf` 로 바꿀 수 있다. 그때도 `ai/` 쪽 구현을 지우지 말고
**대조군으로 남긴다** — 두 결과가 같은지 확인하는 것이 구독이 실제로 값을 하는지 보는 방법이다.
OpenSearch 로 옮기는 선택지도 살아 있다(RRF·정규화가 Apache 2.0). 다만 그건 엔진 교체라
`_project/decisions/017`·`020` 과 함께 다시 봐야 한다.
