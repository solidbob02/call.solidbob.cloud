# 006 — DB 스키마를 도메인 4종에 맞게 정리 (plan 제거, subscriber→customer, closure 재정의)

**작성일**: 2026-08-26
**상태**: 확정

## 맥락

`_project/decisions/004-데모-도메인-4종-확정.md`에서 데모 도메인을 가상 통신사
"한별텔레콤" 단일 시나리오에서 실제 확보 데이터 4종(금융보험·다산콜센터·쇼핑·
질병관리본부)으로 한정했지만, 그때 DB 스키마(`db/schema.sql`, `db/generate_schema_docs.py`)
는 의도적으로 후속 작업으로 미뤄뒀다. 이번 세션에서 실제로 검토한 결과, 아래 세 곳이
여전히 통신 도메인 가정에 묶여 있었다.

1. **`plan`(요금제) 테이블** — `plan_code`/`plan_name`/`monthly_fee`/`data_allowance_gb`.
   4개 도메인 중 "월정액 요금제" 개념을 가진 곳이 없다.
2. **`subscriber`(가입자) 테이블의 `arrears_flag`(체납)·`lost_report_flag`(분실신고)** —
   통신 도메인의 "명의변경 제한 사유"(TERM-5.3)에만 쓰였는데, 그 문서 ID는 지식베이스
   재구성 때 이미 사라졌고, 새 F-2 처리 유형(상품해지·보상·반품·교환) 어디에도
   "명의변경"이 없다.
3. **`closure.closure_type` ENUM('해지','명의변경','보상')과 evidence 컬럼 7개**
   (위약금_안내·잔여할부_안내·고객확인_기록·본인확인_수단·요청경위_확인·사유_근거·
   승인권한_확인) — 전부 통신 약관(`TERM-4.2` 등, 지금은 존재하지 않는 ID)을 근거로
   설계된 필드다.

추가로, `call` 테이블에는 통화가 **어느 도메인**인지 저장할 컬럼 자체가 없었다 —
[3.2절 도메인 라우팅](/docs/03/)에서 지적된 공백이 스키마 레벨에도 그대로 있었다.

## 결정

`db/generate_schema_docs.py`의 `TABLES`를 고치고 재실행해 `schema.sql`·`erd.dot`·
`ERD.png`를 다시 생성했다(17개 → **16개** 테이블).

| 변경 | 내용 |
|---|---|
| `plan` 테이블 | **제거** |
| `subscriber` → `customer` | `plan_code` FK·`arrears_flag`·`lost_report_flag`·`joined_at` 제거. `customer_id`·`first_seen_at`·`status`만 남김. F-3(반복 문의 연결)이 참조하는 "동일 고객" 식별자 역할은 유지 |
| `call` | `subscriber_id` → `customer_id`로 이름 변경 + **`domain` ENUM('finance','dasan','shopping','health') 컬럼 신규 추가**(NOT NULL) |
| `closure.closure_type` | `ENUM('해지','명의변경','보상')` → `ENUM('상품해지','보상','반품','교환')` |
| `closure`의 evidence 컬럼 | 7개(통신) → 10개: 금융보험 상품해지 3개(중도해지수수료_안내·약정혜택소멸_안내·고객확인_기록) + 금융보험 보상 2개(사고경위_확인·귀책여부_확인) + 쇼핑 반품 3개(환불금액_안내·환불기간_안내·상품상태_확인) + 쇼핑 교환 2개(교환가능_확인·재고_확인) |
| `document.document_id`·`compliance_rule.suggestion` 주석 예시 | `TERM-3.2`/`MANUAL-1.4` → `FIN-TERM-3.2`/`FIN-MANUAL-1.4` (도메인 접두어 반영) |

부수적으로 갱신한 것: `jekyll/docs/07-역할분담.markdown`의 인터페이스 계약 JSON 예시(v2
구조는 그대로, 예시 값만 새 스키마로 교체), `jekyll/docs/16-ERD.markdown`, `db/docs/ERD.md`,
`services/core/tests/test_closure_gate_metrics.py`(예시 필드명 동기화).

## 근거

- 사용자가 "DB 스키마 도메인 재검토해서 4개 도메인 결정한 것에 맞게 잘 됐는지 확인하고,
  이외 도메인 내용이 남아 있으면 정리해달라"고 명시적으로 요청.
- F-2는 종결형 처리가 있는 금융보험·쇼핑에만 적용되고([1.4절](/docs/01/)), "명의변경"은
  두 도메인 어디에도 없는 처리 유형이므로 관련 컬럼을 남겨둘 이유가 없었다.
- `call.domain`은 검색·F-2 라우팅에 반드시 필요한 정보인데 스키마에 자리가 없었던 것은
  단순 누락이지, 의도적 설계가 아니었다.
- `subscriber`(가입자)라는 이름은 통신/구독 서비스에 특화된 표현이라, 다산콜센터(민원인)·
  질병관리본부(상담 문의자) 같은 비구독형 도메인에는 맞지 않는다. `customer`(고객)로
  바꾸고 통신 전용 플래그를 제거하는 편이 4개 도메인 전체에 정직하다.

## 되돌리는 법

`db/generate_schema_docs.py`의 `TABLES`에서 `customer`/`call`/`closure` 정의를 이전
커밋(이 결정 이전) 상태로 되돌리고 `python db/generate_schema_docs.py`를 다시 실행하면
`schema.sql`·`erd.dot`·`ERD.png`가 함께 원복된다. `jekyll/docs/07,16`·`db/docs/ERD.md`도
같은 커밋에서 되돌린다.

## 영향받는 범위 — 아직 안 끝난 것

| 항목 | 상태 |
|---|---|
| `call.domain`을 실제로 언제·어떻게 채울지(도메인 라우팅 로직) | **미결** — [3.2절](/docs/03/), `open-items.markdown` |
| 인터페이스 계약(WebSocket/REST) 메시지에 `domain` 필드를 명시적으로 넣을지 | **미결** — 현재는 서버가 `call_id`로 `call.domain`을 조회하는 방식만 가정 |
| `closure` evidence를 넓은 표로 둘지 EAV로 둘지 | **미결 — 기존부터 논의 중** ([`db/docs/ERD.md`](https://github.com/solidbob02/call.solidbob.cloud/blob/main/db/docs/ERD.md) 팀 교차검증 체크리스트), 이번 정리로 없어지지 않음 |
| 실제 MySQL 인스턴스에 이 DDL을 적용하는 마이그레이션 | **미착수** — 지금까지 스키마는 설계 문서 단계이며 실제 DB에 적용된 적이 없다 |
