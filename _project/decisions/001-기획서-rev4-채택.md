# 001. 기획서 rev.4(3인 팀 버전) 채택 및 보완지시서 반영

- **날짜**: 2026-08-25
- **상태**: 채택
- **관련**: `_project/plan.md`, `_project/rev4-보완지시서.md`, `_project/plan-rev4-alt-5인안.md`

## 맥락

카카오톡으로 받은 기획서가 5종(초판 / rev.2 / rev.3 / rev.4 두 갈래)에 보완지시서까지 있어,
어느 것이 현재 판인지 확정해야 저장소 문서를 갱신할 수 있었다. 저장소에는 초판(561줄)이 들어와 있었다.

## 선택지

두 개의 rev.4 가 같은 시각(2026-08-25 10:59)에 전달되었고 계보가 다르다.

| | A. `rev4.md` (1,025줄) | B. `rev4 (1).md` (1,268줄) |
|---|---|---|
| 팀 | **3인 실명** — 정성윤 / 류준 / 장민석, 부하 경고 7.2절 포함 | 5인 트랙(①~⑤), 이름 없음 |
| 트리거 허용 창 | 0 ~ 800ms | −300ms ~ +1,500ms |
| 생성 폴백 | F-2 폴백만 | 생성 폴백 모드 명시 |
| 골든셋 1주차 | 10개 | 10~20개 |
| 부록 | A·B·C | A·B·C·D(내부 참고 자료 분리) |

## 결정

**A(3인 실명 버전)를 기준 판으로 채택**하고, `rev4-보완지시서.md` 의 권장 항목(1~3)과 선택 항목 중 4·5를
저장소 문서에 반영한다. B는 참고용으로 `plan-rev4-alt-5인안.md` 에 보존한다.

## 근거

1. **보완지시서(2026-08-25 10:39 작성)가 A를 대상으로 쓰였다.** 서두에 "대상: rev.4 (3인 팀 버전)"이라 명시하고,
   본문에서 800ms 허용 창을 현행으로 전제해 지적한다 — 이는 A의 값이다.
2. **보완지시서 8절이 B의 제안을 명시적으로 기각했다.** "트리거 허용 창 하한 −300ms / rev.4의 하한 0ms / **rev.4가 낫다**"
   — B의 −300ms 하한을 검토한 뒤 A의 0ms 를 택했다. 즉 보완지시서 시점에 이미 A가 기준이었다.
3. **팀 구성이 실물이다.** A만 실제 3인의 이름과 담당·부하 완화 조치를 담고 있다. 이 프로젝트의 미결 항목
   OI-01(인원 구성)이 A로 해소된다.
4. 파일 수정 시각은 판단 근거가 되지 못한다. 두 파일 모두 전달 시각이 동일하다.

## 반영 범위

| 보완지시서 항목 | 반영 |
|---|---|
| 1. 트리거 허용 창 800ms → **0~1,500ms** + 지연 분포(p50/p95) 기록 + 1주차 침묵 임계값 결정 | 반영 |
| 2. **생성 단계 폴백 모드**(GPU 미확보 시 검색 스니펫만 표시) | 반영 |
| 3. **F-2 순환 검증 한계** 명시 + 규정 작성·스키마 구현·골든셋 라벨링 담당 분리 | 반영 |
| 4. C-5 배정을 P1~P5(정규식) / P6~P7(NER)로 분리 | 반영 |
| 5. 아키텍처 "rev.3에서 변경 없음" → "구성요소 추가 없음, 내부 모듈 명시" | 반영 |
| 6. 개별 사건 자료 내부 보관 | 해당 없음 — rev.4가 이미 본문에서 제거했고 별도 자료를 받지 않았다 |

## 결과 / 되돌리는 법

- `_project/plan.md` 는 A의 **원본 사본**이며 수정하지 않는다. 보완지시서와 충돌하는 값
  (800ms vs 1,500ms)은 **보완지시서가 우선**하며, 사이트 문서에는 1,500ms 로 기재한다.
- 되돌리려면 `plan-rev4-alt-5인안.md` 를 `plan.md` 로 교체하고, 3인 기준으로 고친
  `4-schedule.md`·`milestones.yml`·표지의 팀 정보를 5인 트랙으로 되돌려야 한다.
