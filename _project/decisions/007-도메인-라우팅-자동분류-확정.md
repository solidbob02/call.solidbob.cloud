# 007 — 도메인 라우팅을 자동 분류로 확정 + 지식베이스 팀 리뷰 완료

**작성일**: 2026-08-26
**상태**: 확정

## 맥락

[3.2절 도메인 라우팅](/docs/03/)에서 [4개 데모 도메인](/docs/01/)을 지원하면서 통화가
어느 도메인인지 검색 모듈이 알아야 하는 문제가 생겼다고 적어뒀고, "통화 시작 시 수동
선택 vs 첫 발화 자동 분류" 두 방식을 미결로 남겨뒀다(`open-items.markdown`).

같은 흐름으로 `knowledge-base/`(도메인별 4폴더 재구성) 팀 리뷰도 대기 중이었다
(`w1-knowledge-base.md`).

## 결정

1. **지식베이스 팀 리뷰 완료** — 정성윤·장민석·조서희 팀 회의로 마무리. 4개 도메인
   구조(`finance`/`dasan`/`shopping`/`health`)와 문서 내용 확정.
2. **도메인 라우팅 방식 = 자동 분류**(수동 선택 안 함). 상담원이 통화 시작 시 도메인을
   고르게 하지 않고, 시스템이 초반 발화로 자동 판정한다.

## 설계 — 자동 분류를 어떻게 구현하는가

투입자원 목록 밖 도구를 새로 들이지 않는다는 원칙([아키텍처](/docs/03/))을 지킨다.

```
고객 초반 발화(STT 결과)
   ↓
① KcELECTRA 계열 분류기(C-1~C-4 컴플라이언스 분류기와 같은 계열) — 4클래스
   (finance/dasan/shopping/health) 분류, 신뢰도 점수 포함
   ↓
② 신뢰도가 낮으면 폴백: 4개 도메인 인덱스 전부에 하이브리드 검색을 돌려
   최고 스코어 도메인을 채택 (새 도구 없이 기존 검색 모듈 재사용)
   ↓
call.domain 확정 (db/schema.sql, _project/decisions/006)
```

②는 ①이 실패하는 최소 비용의 안전망이지, 기본 경로가 아니다 — 4개 인덱스를 매번
전부 조회하면 레이턴시 예산([4.3절](/docs/04/))을 넘긴다.

## 평가 설계에 반영

새 지표 **B-0 도메인 분류 정확도**를 [평가 설계 6.1절](/docs/06/)에 추가했다. 목표
**≥0.95** — 도메인을 잘못 분류하면 엉뚱한 인덱스 전체에서 검색하는 셈이라, 도메인
내부 검색 지표(Recall@5 ≥0.70)보다 엄격하게 잡는다.

- `services/core/eval/metrics/domain_routing.py` — 정확도 + 오분류 행렬(confusion
  matrix) 계산. 규칙 기반(LLM 채점 배제, [6.2절 원칙 1](/docs/06/))
- `services/core/eval/harness.py`에 `DomainPredictor` Protocol 추가(B-0), 아직 미구현
  이므로 `"측정 불가 — 모듈 미구현"`으로 정직하게 보고([6.2절 원칙 5](/docs/06/))
- 골든셋의 `domain` 필드([골든셋 재작성](/golden-set/), 2026-08-26)를 그대로 정답
  라벨로 재사용 — F-2 케이스(발화 텍스트가 없고 `closure_intent`만 있는 GS-008~010)는
  분류 대상에서 제외된다
- 테스트: `test_domain_routing_metrics.py`(지표 함수 단위), `test_harness.py`(배선
  검증) — `pytest services/core` 전부 통과

## 근거

- 사용자가 "지식베이스 팀 리뷰 마무리, 도메인 라우팅은 자동 분류로 간다"고 명시적으로
  확정.
- 수동 선택은 상담원에게 매 통화 클릭을 요구해 [1.2절](/docs/01/) "통화 후 대신 통화
  중" 개입이라는 프로젝트 정체성과 마찰이 있고, 실무 콜센터에서도 발신 전 상담원이
  도메인을 미리 알기 어려운 경우(대표번호로 걸려온 문의 등)가 있다. 자동 분류가
  실제 가치 제안에 더 가깝다.
- 폴백을 검색 재사용으로 설계해 [보완지시서 2번](https://github.com/solidbob02/call.solidbob.cloud)의
  "생성 폴백 모드"와 같은 논리 — 새 도구 없이 기존 구성요소로 위험을 낮춘다.

## 되돌리는 법

`DomainPredictor` Protocol과 `report["domain_routing"]` 배선을 제거하면 하네스는
이전 상태(도메인 라우팅 지표 없음)로 돌아간다. 수동 선택으로 되돌리려면 [3.2절](/docs/03/)·
[6.1절](/docs/06/)의 관련 문구를 되돌리고, 프론트엔드(조서희 담당, 미착수)에 도메인
선택 UI를 추가하면 된다 — 아직 화면 자체가 없어 되돌리는 비용은 낮다.

## 후속 — fastapi/ 아키텍처 통합 (2026-08-26, 같은 날)

이 문서 본문의 `services/core/eval/...` 경로는 작성 당시 기준이다. 같은 날 `ai` 브랜치의
`fastapi/` 헥사고날 아키텍처를 정본으로 채택하면서(`_project/decisions/006` 참고 패턴과
동일), `domain_routing.py`는 `fastapi/evaluation/metrics/`로, `DomainPredictor` Protocol은
`hub/app/ports/output/domain_routing_port.py`(ABC) + `hub/app/dtos/domain_classification_dto.py`
로 이식됐다. `services/core/`는 삭제됐다. 설계·평가 목표(정확도 ≥0.95)는 변경 없음.
