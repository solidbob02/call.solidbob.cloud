# 017. ES 인덱스는 단일 인덱스 + `domain` 필터로 간다

- **날짜**: 2026-08-27
- **상태**: 채택 (`single` 확정) · 적재 구현 완료 · **ES 기동 확인 대기**
- **관련**: `jekyll/_backlogs/w2-kb-index.md`(이 미결이 막고 있던 티켓),
  `docs/domain.md` §3, `knowledge-base/README.md`,
  `ai/apps/retrieval/adapter/outbound/es_index.py`

> ⚠ **이 결정은 판단이지 실측이 아니다.** Recall@5·MRR 을 재서 고른 것이 아니다.
> 잴 수 있는 상태가 아니었다 — 점수를 내려면 검색 구현체(`RetrievalPort`)가 있어야 하는데
> 그건 `w2-naive-rag` 이고 아직 착수 전이다. 아래 근거는 전부 **메커니즘 수준의 논증**이며,
> 나중에 실측이 뒤집을 수 있다.

## 맥락

지식베이스 청킹·문서 ID 부여는 2026-08-26 에 끝났다(청크 102개, 분할 0건). 그런데
`w2-kb-index` 의 완료 조건 **"같은 명령으로 재적재가 재현된다"** 가 남아 있었고, 그것이
막힌 이유는 코드가 아니라 **미결 하나**였다.

> ES 는 도메인별 별도 인덱스 또는 같은 인덱스의 `domain` 필드 — 어느 쪽인지 미결
> (`docs/domain.md` §3)

"지금 인덱스를 만들면 결정 후 다시 만들어야 한다"는 이유로 적재 자체를 미뤄 뒀고,
그 사이 `w2-naive-rag`(검색)도 함께 멈춰 있었다.

## 결정

**`single` — 인덱스 하나(`callguard-kb-single`)에 전부 넣고 `domain` 필드로 필터한다.**

```
callguard-kb-single    청크 102개 전부 + domain keyword 필터
```

`per-domain` 코드 경로(`callguard-kb-{finance,dasan,shopping,health}`)는 **지우지 않는다.**
아래 "언제 도메인별로 바꾸나" 조건이 참이 되면 그 경로로 전환한다 —
`--layout per-domain` 한 줄이면 되도록 남겨 둔다.

## 근거

**지금 규모에서 나눌 이유가 없다.** 조항이 102개뿐이라 도메인별로 쪼개면 인덱스당
20~34건(health 21 · dasan 20)이 된다.

1. **N 이 작을수록 BM25 IDF 가 불안정하다.** N=21 에서는 문서 한두 건에도 IDF 가 크게
   흔들린다. 단일 인덱스의 N=102 도 작지만 3~5배 안정적이다.
2. **도메인별 인덱스의 실질 이점은 독립 재적재 하나**인데, 전체 재적재가 1초도 걸리지 않는
   지금은 있으나 마나다.
3. **오분류 회복 여지.** B-0 목표가 ≥0.95 이므로 약 5%는 틀린다. 단일 인덱스면 하드 필터
   대신 `should`+boost 로 다른 도메인 문서를 후보에 남길 수 있다. 인덱스가 갈리면 그 선택지가 없다.
4. **매핑이 한 벌이다.** 네 벌이면 nori 사전·차원·유사도 설정이 한 곳만 바뀌어도 도메인 간
   점수가 조용히 비교 불가능해진다.

**속도는 근거가 되지 못한다.** 지식베이스가 39KB 라 어느 쪽이든 샤드 라운드트립 같은 고정비에
묻힌다. 7.3절 내부 처리 p95 ≤1,000ms 에 비하면 차이는 노이즈다. **재지 않았으므로 숫자로 적지 않는다.**

### 반대 방향으로 작용하는 것 (숨기지 않는다)

- **도메인별 IDF 가 그 도메인 안에서는 더 잘 변별할 수 있다.** "환불"이 쇼핑에서 흔하다는
  사실은 쇼핑 안에서 검색할 때 반영되는 게 맞다. 전역 IDF 는 관계없는 분포를 섞는다.
- **1번 근거는 데이터가 커지면 사라진다.** 도메인마다 수만 건이 쌓이면 IDF 는 어느 쪽이든
  안정적이다. 즉 이 결정은 **지금 규모에 대한 결정**이다.

## 언제 도메인별 인덱스로 바꾸나

**볼륨이 커지는 것만으로는 바꾸지 않는다.** 청크 하나가 평균 400바이트라 1000배(10만 청크)가
돼도 40MB 다 — Elasticsearch 샤드 권장 크기(10~50GB)에 한참 못 미친다.

**아래 중 하나가 참이 되면 전환한다.**

| 조건 | 왜 |
|---|---|
| **도메인이 4개를 넘어 크게 늘어난다** (특히 고객사별 KB 로 갈린다면 즉시) | 필터 선택도가 25%에서 1~2%로 떨어지면 **filtered HNSW 의 recall 이 무너진다.** 벡터 검색에서 제일 아픈 지점 |
| **단일 인덱스가 샤드 2개 이상을 필요로 한다** | 단일 인덱스의 핵심 장점인 "전역 IDF" 는 **샤드가 1개일 때만 성립한다.** BM25 점수는 인덱스가 아니라 **샤드 단위**로 계산된다 — 샤드가 늘면 같은 문제가 인덱스 안에서 생긴다 |
| **전체 재색인이 "커피 한 잔" 넘게 걸린다** | 임베딩 모델 교체 때 도메인 하나만 다시 태우는 능력이 실제 가치가 된다 |
| **도메인별로 보존기간·업데이트 주기·권한이 갈린다** | 인덱스가 수명주기·RBAC·장애 반경의 단위다 |

### 전환 방법 (미리 정해 둔다)

둘 중 하나를 고르는 게 아니라 **alias 를 앞에 세운다.**

```
쓰기:  callguard-kb-{finance,shopping,health,dasan}     도메인별 인덱스
읽기:  callguard-kb  (alias — 위 전부를 가리킨다)         B-0 폴백은 여기로
```

도메인 지정 검색은 해당 인덱스를 직접, 신뢰도가 낮을 때의 전체 검색은 alias 하나를 친다.
**소비 측(`RetrievalPort` 구현체)은 이름 하나만 알면 되므로 바뀌지 않는다.**

중간 단계로 `_routing=domain` 도 있다 — 단일 인덱스를 유지하면서 같은 도메인 문서를 같은
샤드에 모아 지역성만 얻는다. 인덱스를 나누기엔 이르고 샤드는 여럿일 때 쓴다.

## 지금 고정해 둔 것

두 레이아웃의 **문서 본문·매핑·애널라이저가 동일하다** — `per-domain` 에도 `domain` 필드를
남긴다. `number_of_shards` 는 **1** 로 못박았다(BM25 term statistics 가 샤드 단위라,
샤드 수가 다르면 나중 비교의 교란 변수가 된다). 덕분에 전환이 **재적재 한 번**으로 끝난다.

## 주의

- `callguard-kb-*` 와일드카드는 **두 레이아웃을 한꺼번에 잡는다.** 양쪽을 동시에 적재해 둔
  상태라면 같은 조항이 두 번 세어진다. 인덱스 이름은 반드시 `index_names(layout)` 로 얻는다.
- 임베딩(`dense_vector`, KoE5 1024차원)은 아직 매핑에 없다. 4주차에 매핑을 늘리고 재적재한다.
- **nori 는 `analysis-nori` 플러그인이다.** 설치하지 않으면 인덱스 생성이 실패한다
  (`docker-compose.yml` 이 기동 시 설치한다).

## 되돌리는 법

`--layout per-domain --recreate` 로 다시 적재하고, `callguard-kb-single` 을 지운다.
코드는 이미 양쪽을 다 지원하므로 수정할 것이 없다.
`w2-naive-rag` 이후에는 골든셋 `v1-50` 의 B 케이스 14건으로 **양쪽을 실측해** 이 판단이
맞았는지 확인할 수 있다 — 그때 수치가 나오면 이 문서에 덧붙인다.
