## 맥락

002에서 7.3절 초안을 그대로 확정했으나, 정성윤이 실제 `db/schema.sql`·`golden-set/v1-10.json`·
`services/core/eval/golden_set.py`와 필드 단위로 대조해 "조건부 컨펌"으로 회신했다. 계약 예시가
일부만 보여주는 값(`verdict: "blocked"`만 등장, `evidence` 7개 컬럼 중 3개만 등장)이라 눈에
안 띄었던 불일치였다. 내가(류준) 각 주장을 코드로 직접 재확인했다 — 아래 표는 실제 확인 결과다.

| 주장 | 확인 결과 |

| `evidence`는 `closure_type`별 부분집합 | `db/schema.sql:137-154` closure 테이블 확인 — 위약금_안내·잔여할부_안내·고객확인_기록(해지 전용) / 본인확인_수단·요청경위_확인(명의변경 전용) / 사유_근거·승인권한_확인(보상 전용), 컬럼 코멘트에 전용 표기까지 있음 — 사실 |
| 전사 이벤트에 발화 식별자 없음 | `db/schema.sql:52-53 transcript_segment.segment_id` 존재, 계약에는 없었음 — 사실. interim 199건/20초(V4 실측)가 `call_id`만으로는 구분 불가하다는 지적도 타당 |

4건(🔴) 전부 사실로 확인되어 그대로 반영한다. 🟡(정하면 되는 것) 5건은 내가 판단해 결정한다.

## 결정 — 🟡 항목

| 항목 | 결정 | 근거 |
|---|---|---|
| `span` 오프셋 | 문자(코드포인트) 기준 | `masking_event.span_start/end`가 INT이고, byte 기준이면 한글(UTF-8 3바이트)에서 프론트·백이 어긋난다. 다른 안이 없다 |
| `score` 필드명 | `similarity_score`로 통일 | DB 컬럼명과 맞춰 직렬화 매핑 코드를 없앤다. 프론트가 짧은 이름을 선호하면 이후 API 레이어에서 alias 하면 된다 |
| RRF 원점수 | 계약에 넣지 않는다. `eval_run`/`eval_result` 로그로만 남긴다 | 계약은 화면 표시용이고 원점수는 실험용 — 정성윤 제안 그대로 채택 |
| `rank` | 별도 필드 없음, 배열 순서 = rank | `recommendation_card.rank`는 있지만 배열 순서로 이미 표현되므로 필드 중복을 만들지 않는다 |
| latency 정의 | `internal_latency_ms` = 트리거 발동 → 카드 응답 완료 / `e2e_latency_ms` = `utterance_end_ms` → 화면 표시 | 정성윤 제안 채택. V4 실측(발화 종료 +346ms)이 `e2e_latency_ms`에 포함된다는 점을 명시해둔다 |

## 결정 — 트리거 v1 설계 (정성윤 조건 2)

**3주차 v1은 자체 침묵 타이머 대신 Google STT의 `is_final`(엔드포인팅)에 올라탄다.** 자체로 700~1,000ms
무음을 또 기다리면 STT 자체 지연(+346ms, V4 실측)과 이중으로 쌓인다. `is_final: true`가 오는 시점을
곧 발화 종료로 보고, 거기서 트리거 판정(10ms 예산)만 더한다.

이 설계가 [4.1절](/docs/04/) 1,500ms 허용 창의 실제 근거가 된다 — "침묵 대기 최대 1,000ms"가 아니라
**"STT 엔드포인팅 지연(+346ms 실측) + 판정·큐잉 여유"**로 바뀐다. 4.1절에 이 산식을 반영한다.

## 결정 — 평가 하네스 (정성윤 조건 1)

`aggregate_trigger`가 on_time/early/late 비율만 내고 지연시간 분포(p50/p95)를 계산하지 않던 문제를
`services/core/eval/harness.py`에서 해결했다 — `run_eval`이 트리거 delta 리스트를 모아
`metrics/latency.py`의 `summarize_latency`로 p50/p95/p99를 함께 리포트에 싣는다
(`report["trigger"]["latency_ms"]`). 새 지표 모듈을 만들지 않고 기존 `latency.py`를 재사용했다.
