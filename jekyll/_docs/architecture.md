> **구성요소 추가 없음.** 새 DB·검색엔진·통신 프로토콜·투입자원 목록 밖 도구를 도입하지 않았다.
> 단, 이전 리비전 다이어그램에서 생략돼 있던 **C-5 마스킹 모듈, F-2 게이트 모듈, MySQL 테이블 구성**을
> 명시적으로 표기했다. 기존 FastAPI 코어와 MySQL 내부를 세분화한 것이며 신규 인프라가 아니다. (보완지시서 5)

```
[상담원 브라우저]  React 대시보드 (자막 / 카드 / 경고 / 종결 모달)
       │
   WebSocket (양방향)
       │
[Node.js 게이트웨이]   오디오 청크 중계 / 자막·카드·경고 푸시
       ├──→ [Google STT] ──→ 부분 전사 결과
       ▼
[FastAPI 코어]
       ├─ C-5 마스킹 모듈 ──→ 자막·저장 양쪽 앞단
       ├─ 트리거 판정 모듈   발화 완결성 · 침묵 길이 · 의도 신호
       ├─ 검색 모듈 ──→ [Elasticsearch]  nori(BM25) + dense_vector + RRF
       ├─ 생성 모듈 ──→ [HF Transformers] 근거 기반 요약 (폴백 시 생략)
       ├─ 컴플라이언스 모듈 ──→ [분류기]
       └─ F-2 게이트 모듈 ──→ 같은 ES 인덱스 조회 + 규칙 판정
       ▼
   [MySQL]
     ├─ call            통화 메타
     ├─ transcript      마스킹된 전사
     ├─ recommendation  추천 이력
     ├─ closure         종결 사유 + 근거 필드   ← F-2
     └─ eval_result     평가 결과
```

## 도구별 역할

| 도구 | 역할 | 필수도 |
|---|---|---|
| Python / FastAPI | 검색·생성·게이트 API, 백엔드 전체 | 필수 |
| Node.js / WebSocket | 실시간 양방향 게이트웨이 | 필수 |
| Google STT | 스트리밍 음성인식 + 화자 분리 | 필수 |
| Elasticsearch | nori + dense_vector 하이브리드 검색 | 필수 |
| **HuggingFace Transformers** | **① 임베딩 ② 컴플라이언스 분류기 ③ 카드 요약 생성** | 필수 |
| React | 상담원 대시보드 | 필수 |
| MySQL | 통화 메타·전사·추천·종결·평가 결과 | 필수 |
| Docker | 서비스 컨테이너화 | 필수 |
| matplotlib | 성능 곡선, 레이턴시 분포 | 필수 |
| Kubernetes / AWS / VirtualBox | 배포·테스트 | 선택 |

OpenCV는 이 주제에 활용처가 없어 사용하지 않는다.

## 생성 모델과 캐시

- **생성 모델**: 상용 API를 도입하지 않는다. HF Transformers로 **소형 한국어 오픈 모델**을 로드해 카드 요약을 생성한다. 검색된 근거를 2~3문장으로 다듬는 제한된 작업이라 대형 모델이 필요 없다.
- **폴백 모드**: GPU 미확보 또는 첫 토큰 500ms 초과 시 **생성 없이 검색 원문 스니펫만 표시**하는 모드를 기본값으로 전환한다. 출처 표시와 "관련 문서 없음" 처리는 그대로 동작하므로 **"찾아주는 것"이라는 핵심 가치는 유지된다.** → [2. 개발 요구 사항]({{ '/docs/2-requirements/#4-실시간-문서-추천-처리--rag-핵심' | relative_url }})
- **캐시**: 별도 저장소를 두지 않는다. 프로세스 인메모리 LRU + MySQL 영속화.

## 데이터 모델

MySQL은 여섯 묶음으로 구성한다 — **통화**(`call`) · **전사**(`transcript`, 마스킹 구간) · **추천**(`recommendation`, 카드) · **컴플라이언스**(감지 이력) · **종결**(`closure`, F-2 요건) · **평가**(측정 실행과 지표).

컬럼 정의와 관계는 **ERD로 관리한다.** Mermaid 소스가 정본이고 이미지는 산출물이며, 둘 다 저장소의
`docs/erd/`에 있다 (`schema.mmd` · `schema.png`).

초안은 마스킹 구간·카드·요건 충족 여부를 JSON 컬럼에 담고 있었다. 그 형태로는 **5주차 마스킹 재현율 곡선과 7주차 지식베이스 공백 리포트를 SQL로 집계할 수 없어**, 3NF 기준으로 정규화해 16개 테이블로 분해했다.
분해 근거와 트레이드오프는 `docs/erd/normalization.md`, 테이블별 설명과 재생성 절차는 `docs/architecture.md` 참조.

16개를 한 번에 만들지 않는다. 3주차 코어(전사·마스킹) → 추천 → 1주차 평가 계열 순으로 만들고, 종결 계열은 F-2가 7주차 체크포인트를 통과할 때 만든다.

> **미확정**: 컴플라이언스 경고(C-1~C-4)를 별도 테이블로 둘지 `recommendation`에 통합할지 정하지 않았다.
> 정규화 관점에서는 별도 테이블을 권고한다. 1주차 스키마 확정 때 함께 정한다.
