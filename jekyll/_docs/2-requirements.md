## 1) 목적

통화 중 발생하는 고객 질의에 대해 **1초 이내에 근거 문서를 상담원 화면에 제시**하고, 그 과정에서 **개인정보가 화면·DB에 평문으로 남지 않게** 한다. 단순히 동작하는 데모가 아니라 **품질을 수치로 측정하고 회귀를 자동으로 막는 체계**까지를 개발 범위에 포함한다.

## 2) 개발 범위

### 포함

| 구분 | 내용 |
|---|---|
| 음성 | 스트리밍 STT 연동, 화자 분리, 발화 구간 검출 |
| 검색 | 문서 수집·청킹·ID 부여·색인, 형태소·벡터 하이브리드 검색, 리랭킹 |
| 실시간 | 트리거 판정, WebSocket 양방향 전달, 레이턴시 최적화·캐싱 |
| 생성 | 근거 기반 요약 카드(스트리밍 출력), 출처 표시, 근거 부족 시 거절, **폴백 모드** |
| 분류 | 컴플라이언스 분류기 파인튜닝 |
| **마스킹** | **C-5 개인정보 실시간 마스킹 (P1~P7)** |
| 게이트 | F-2 종결 요건 검증 (조건부) |
| 후처리 | 상담 요약, 유형 분류, 지식베이스 공백 리포트 |
| 평가 | 골든셋 구축, 자동 채점 하네스, 오류 주입 실험, CI 연동 |

### 제외

| 제외 항목 | 사유 |
|---|---|
| OpenCV 기반 영상 처리 | 본 주제에 활용처가 없다 |
| 자체 통화 녹음 수집 | 개인정보. 공개된 저작권 해결 데이터만 사용 |
| 약관 원문의 공개 게시 | 저작권. 화면·문서에는 요약·해석 + 출처만 |
| 실제 콜센터 회선(PBX/CTI) 연동 | 8주 범위 밖. 브라우저 오디오 입력과 녹음 파일 재생으로 대체 |
| 위험도 점수화·표시, 당사자 자동 응답 | 부록 A 원칙. 시스템은 상담원을 돕는 도구로만 존재한다 |
| 상담원별 누적 지표 | 감시 도구로 전용될 수 있다 |

## 3) 음성 데이터 수집 및 연계

| 요구 | 내용 |
|---|---|
| A-1 | Google STT 스트리밍 인식, 부분 결과(`is_final: false`) 포함 수신 |
| A-2 | 화자 분리 — 고객 / 상담원. **채널 분리 또는 diarization** |
| A-3 | 브라우저 ↔ 게이트웨이 오디오 청크 및 자막 전달 (WebSocket) |
| A-4 | 발화 구간 검출 — 침묵 판정 |

> **A-2 전제 확인**: 실무 콜센터는 대개 2채널 스테레오로 화자가 물리 분리돼 diarization이 불필요하다. AI Hub 데이터의 채널 구성에 따라 난이도가 갈리므로 **1주차에 반드시 확인한다(V1)**. 모노일 경우 시연은 물리 2채널(브라우저 2대)로 우회하고 그 사실을 한계로 명시한다.

**평가용 음성**은 AI Hub 공개 데이터를 1순위로 사용하며 **1주차 즉시 신청**한다. 반복 실험은 녹음 파일 배치 모드로 수행하고 스트리밍 API는 실시간 데모에만 쓴다(비용 통제).

실제 데이터가 쓰이는 곳과 아닌 곳을 구분한다.

| 용도 | 데이터 |
|---|---|
| STT 파이프라인 동작 검증, 데모 | AI Hub 실제 음성 |
| 오류 내성 실험 | **텍스트 레벨 통제 오류 주입** |

## 4) 실시간 문서 추천 처리 — RAG 핵심

| 요구 | 내용 |
|---|---|
| B-1 | **검색 트리거 판정** — 언제 검색할지 결정 |
| B-2 | **하이브리드 검색** — nori 형태소(BM25) + dense_vector, RRF 병합 |
| B-3 | 리랭킹 — 상위 후보 재정렬 |
| B-4 | 근거 기반 요약 카드 생성 (스트리밍 출력) |
| B-5 | 출처 표시 — 문서명 + 조항 + 유사도 |
| B-6 | 근거 부족 시 **"관련 문서 없음"** 반환 |

### 난제 ① 트리거 판정 — 언제 검색할 것인가

```
0.4초  "아"          1.6초  "아 저번에 가입할"
0.9초  "아 저번에"    3.1초  "아 저번에 가입할 때 6개월 할인 된다고 했는데"
```

매 조각마다 검색하면 서버 과부하·카드 깜빡임, 너무 늦으면 대화가 이미 넘어간다.

| 전략 | 방법 | 예상 문제 |
|---|---|---|
| 침묵 기반 | N초 무음 시 검색 | 말이 느린 고객에서 지연 |
| 종결어미 기반 | "~요", "~까요", "~는데" 패턴 | 중간에 끊어 말하면 오발동 |
| 길이 기반 | 토큰 N개 누적 시 | 의미와 무관하게 발동 |
| 하이브리드 | 위 조합 + 디바운싱 | 튜닝 복잡 |

**"적절한 시점"의 정의** — 규칙 기반 채점을 위해 허용 창을 고정한다.

> 골든셋의 각 질문에 **발화 종료 시각**을 라벨링한다.
> **발화 종료 후 0 ~ {{ site.data.metrics.targets.trigger.window_ms_max }}ms 이내 발동을 "적절"로 판정한다.**
> 0ms 이전 발동은 조기 발동, 상한 초과는 지연 발동으로 각각 별도 집계한다.

> ⚠ **보완지시서 1 반영**: 이 값은 rev.4의 800ms에서 넓힌 것이다. 침묵 기반 트리거는 정의상 무음 N(일반적으로 700~1,000ms)을 기다린 뒤 발동하므로, 800ms 창에서는 3주차 v1이 **구조적으로 목표를 달성할 수 없었다.** 지표가 구현을 평가하는 것이 아니라 구현 방식을 사전에 배제하는 상태였다.
> 조건: `허용 창 상한 > 침묵 임계값 N + 트리거 판정 지연(10ms)`. **1주차에 N을 정하고 이 부등식을 확인한다.**
> 합격선과 별개로 **트리거 지연 분포(p50/p95)를 기록한다.** "v1 침묵 기반 p50 920ms → 종결어미 하이브리드 p50 610ms" 같은 문장이 지표 하나보다 강하다.

### 난제 ② STT 오류 내성 — 본 사업의 대표 실험

| 실제 발화 | STT 결과 | 문제 |
|---|---|---|
| 해지 | 해제 | 완전히 다른 조항이 검색됨 |
| 요금제 | 요금 제 | 띄어쓰기로 형태소 분해 실패 |
| 위약금 | 위약 금 | 동일 |

```
1. nori 형태소 분석기 → 띄어쓰기 오류 흡수
2. 자모 분해 필터      → 유사 발음 오인식 대응
3. dense_vector 필드   → 의미 기반 검색
4. RRF 병합            → 위 결과 통합
```

오류율 0~20%를 통제하며 주입해 **BM25 / 벡터 / 하이브리드 / C-5 마스킹 재현율**을 같은 축에서 비교한다. 이 실험은 실제 데이터 부족을 대체하는 합성이 아니라 **구간별 비교를 위해 오류율을 통제한 설계**다. 실제 통화로는 5%/10%/15% 곡선을 그릴 수 없다.

### 난제 ③ 레이턴시 예산 — 두 지표를 분리한다

| 지표 | 구간 | 목표 |
|---|---|---|
| **내부 처리 지연** | 트리거 발동 → 카드 표시 | p95 ≤ {{ site.data.metrics.targets.latency.internal_p95_ms }}ms |
| **E2E 체감 지연** | 발화 종료 → 카드 표시 | 측정·기록 (목표 미설정) |

E2E에는 STT 부분 결과 반환 지연, 게이트웨이 홉, 브라우저 렌더링이 포함된다. 통제 밖이므로 목표를 걸지 않되, **통제 가능한 구간과 아닌 구간을 분리했다는 사실 자체를 성과로 기록한다.**

| 단계 | 목표 | 수단 |
|---|---|---|
| 트리거 판정 | 10ms | 규칙 우선 |
| 검색 | 150ms | 인덱스 워밍업, 필드 최소화 |
| 리랭킹 | 200ms | 상위 20개만, 배치 추론 |
| 생성 | **첫 토큰 500ms** | 스트리밍 출력 — 카드 점진 표시 |
| 전송 | 50ms | WebSocket 유지 연결 |

### 생성 폴백 모드 (보완지시서 2)

GPU를 확보하지 못하거나 첫 토큰 500ms를 맞추지 못하면 **생성 없이 검색 원문 스니펫을 표시하는 모드**로 기본값을 전환한다.

| 모드 | 카드 내용 | 레이턴시 |
|---|---|---|
| 생성 모드 | 근거를 2~3문장으로 요약 | 검색 + 리랭킹 + 생성 |
| **폴백 모드** | **검색된 원문 스니펫 + 출처** | 검색 + 리랭킹 (생성 단계 제거) |

폴백에서도 B-5(출처 표시)와 B-6("관련 문서 없음")은 그대로 동작한다. 상담원이 얻는 핵심 가치인 **"찾아주는 것"은 유지된다.**

이것은 리스크 대응이자 실험 조건이다. 두 모드를 비교하면 **생성 단계가 실제로 얼마나 기여하는지** 수치로 말할 수 있고, 토큰 비용 대비 효용을 논할 근거가 생긴다.

## 5) 개인정보 마스킹 (C-5) — 코어

이 시스템은 실시간 자막을 화면에 띄우고 전사를 DB에 저장한다. 마스킹이 없으면 그 자체가 설계 결함이다.

| 항목 | 처리 |
|---|---|
| 적용 지점 | ① 화면 자막 표시 전 ② MySQL 저장 전 — **양쪽 모두** |
| 원본 보관 | 하지 않음. 마스킹된 형태만 저장 |
| 착수 | **3주차 — 자막 구현과 동시에** |

**탐지 파이프라인** — STT 출력은 정형 문자열이 아니므로 정규화가 선행된다.

```
STT 전사 결과
  ① 구분자·공백 제거 후 연속 숫자열 판정   ← 주 실패 모드
  ② 한글 수사 → 숫자 변환 (보조)
  ③ 패턴 매칭(정규식) + NER(이름·주소)
  ④ 마스킹
```

Google STT 한국어는 긴 숫자열을 대체로 아라비아 숫자로 정규화하므로, 한글 수사보다 **구분자 부재와 띄어쓰기 붕괴**가 지배적 실패 모드다. ①을 ②보다 앞에 둔다.

| # | 패턴 | 방식 | 담당 |
|---|---|---|---|
| P1 | 주민등록번호 (13자리) | 정규식 | 인프라 |
| P2 | 카드번호 (14~16자리) | 정규식 | 인프라 |
| P3 | 계좌번호 (10~14자리) | 정규식 | 인프라 |
| P4 | 휴대전화번호 | 정규식 | 인프라 |
| P5 | 인증번호 (4~6자리, 문맥 조건) | 정규식 + 문맥 | 인프라 |
| **P6** | **인명** | **NER** | **AI** |
| **P7** | **상세주소** | **NER** | **AI** |

> **보완지시서 4 반영**: P6·P7은 정규식이 아니라 HF 모델 로드·튜닝이 필요한 AI 작업이므로 인프라 담당에서 분리했다. 5주차 마스킹 재현율 곡선도 오류 주입 스크립트와 맞물리므로 AI 담당이 가져간다. 일정이 밀리면 **절대 규칙의 범위를 P1~P5로 한정**하고 그 사실을 지표와 한계에 명시한다.

**지표 우선순위**: 누락 0건 > 과잉 마스킹 억제. **애매하면 가린다.** 과잉 마스킹률은 목표가 아니라 참고 기록이다.

## 6) 상담원 지원 화면 기능

| 요구 | 내용 |
|---|---|
| 자막 | 화자별 실시간 자막. **마스킹 적용 후** 표시. 부분 결과는 갱신, 최종은 확정 |
| 추천 카드 | 출처 없는 카드는 표시하지 않는다. 카드가 없으면 "관련 문서 없음" |
| 경고 | 컴플라이언스 감지 시 발생 시각과 권장 대체 표현 함께 표시 |
| 종결 모달 | F-2 게이트 — 필요 근거 체크리스트, 차단 사유, 근거 문서 출처 |
| 연결 | WebSocket 유지 연결. 끊김 시 재연결 및 세션 복구 |

메시지 규격은 [인터페이스 계약]({{ '/docs/interface-contract/' | relative_url }})이 정본이며 1주차에 확정한다.

## 8) 보안 및 개인정보 보호

| 항목 | 요구 사항 |
|---|---|
| 민감정보 마스킹 | C-5로 자막·저장 양쪽 앞단에서 처리. 원본을 보관하지 않는다 |
| 데이터 출처 | 자체 녹음을 수집하지 않는다. AI Hub 등 저작권·개인정보가 해결된 공개 데이터만 |
| 저작권 | 약관 원문은 검색 인덱스 내부 저장까지만. 화면·공개 문서·발표 자료에는 요약·해석 + 출처 |
| 자격증명 | API 키는 `.env`로 관리하며 저장소에 커밋하지 않는다 |
| 답변 범위 제한 | LLM은 인덱싱된 문서 범위 밖의 정책·보상을 말하지 않는다 |
| **판정과 설명의 분리** | **판정은 규칙이 한다.** 종결 가능 여부·요건 충족·마스킹 대상·기관 매칭은 전부 결정론적 로직. LLM은 판정 결과를 사람이 읽을 문장으로 옮기는 역할만 |
| 시스템의 발언 범위 | "위험 신호가 감지되었습니다"는 가능. **"안전합니다"는 말하지 않는다** |
| 공개 경계 | 본 저장소는 GitHub Pages로 공개 게시된다. 커밋이 곧 발행이다 |
